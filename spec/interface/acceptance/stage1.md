# 段階1 受け入れチェックの記録

- 対象: base / platform / jobs、codec、dsp と SIMD 抽象、io、bank / buildtool
- 日付: 2026-11-15
- 判定: **5 組とも受け入れ**（下記の持ち越し事項つき）
- 進め方: 実装（Opus）→ 実装者とは別のエージェントによる独立テスト（Opus）→ 欠陥の差し戻しと修正 → 修正の再確認 → 受け入れチェック（Fable）→ マージ

## 確認したこと

受け入れ側で新規ビルドディレクトリから作り直した結果。どの構成も警告 0。

| 組 | 構成 | 結果 |
| --- | --- | --- |
| codec | gcc Debug、clang Release、gcc thread、gcc address,undefined | 全件通過 |
| base / platform / jobs | gcc Release（並行テスト 18 本を 20 回）、clang Debug、gcc thread（14 本を 8 回）、gcc address,undefined | 全件通過、繰り返しで失敗なし |
| dsp と SIMD | gcc Release、gcc address,undefined、clang Release `-mavx2 -mfma`、`SND_SIMD_SCALAR=ON` | 全件通過 |
| io | gcc Debug、gcc Release（10 回）、gcc thread（3 回）、gcc address,undefined | 全件通過、繰り返しで失敗なし |
| bank / buildtool | gcc Debug、gcc Release、gcc address,undefined、clang Release、gcc thread | 全件通過 |
| 全部をマージした状態 | gcc Debug、gcc Release、gcc address,undefined、clang Release | 62/62 通過 |

受け入れ側でコードを読んだ箇所: デコーダプール（ロックフリーの空きリストと世代）、RT ワーカー（チャンクの取得・締切・静止判定）、スナップショットの読み出し、エフェクトの初期化、IO スケジューラの不変条件、既定ファイルシステムの開き方、バンク形式 2.0 のヘッダ。

未確認: clang のサニタイザ（環境にランタイムが無い）、NEON 経路（構文検査のみ）、Linux 以外の OS、`openat2` が使えない環境のフォールバック。

## 独立テストで見つかって直した欠陥

| 組 | 件数 | 主なもの |
| --- | --- | --- |
| codec | 1 | シーク位置の計算の桁あふれ |
| base / platform / jobs | 9 | RT ワーカーの静止判定が早すぎる、タイマーデバイスの締切計算が約 106 時間で桁あふれ、スナップショットが過去へ戻る、通常ワーカーの終了処理との競合 |
| dsp と SIMD | 13 | エフェクトの初期化漏れ（範囲外アクセス）、スカラー経路の積和が暗黙に融合される、sinc リサンプラの折り返しが比率 5 超で崩れる、ピッチシフターの遅延の報告 |
| io | 7 | デッドロック 2 件、終了処理との競合、FIFO で IO スレッドが止まる |
| bank / buildtool | 18 | 取り消しで別のバンクの登録が消える、ヘッダ後半がチェックサムの範囲外（形式 2.0 で解消）、ディレクトリを渡すと異常終了、生成ヘッダの識別子がマクロと衝突 |

受け入れ側が仕様の穴に対して下した決定は、各モジュールのヘッダのコメントと README に反映してある。

## 持ち越し事項

契約の変更が要るもの（契約 1.1 としてまとめて反映する）:

| # | 内容 | 出どころ |
| --- | --- | --- |
| A1-1 | 締切に遅れたチャンクのワーカーは、次のブロックに入っても前のブロックの入出力に触る。core 側の規則（世代での二重化と、`RtWorkerPool` の SAFE POINT の使い方）を契約に書く | jobs |
| A1-2 | `RealVoice.resamplerState`（64 バイト）に高品質リサンプラの状態が収まらない。状態の置き場所を決める | dsp |
| A1-3 | Stream テーブルは行が動くので、IO スレッドとデコードジョブが列へ直接書けない。外部の書き手の列の置き方を決める | io |
| A1-4 | `snd_effect_desc` にサンプルレートが無く、プラグインが状態サイズを見積もれない | dsp |
| A1-5 | buildtool が dsp に依存できず、DSP プール必要量の算出関数を呼べない | dsp, buildtool |
| A1-6 | 標準エフェクトの種別 ID と、組み込みコーデックのバイト配置が bank-format.md に無い | dsp, codec |
| A1-7 | `snd_result` に「同じバンクが既にロード済み」が無い。言語名をランタイムに伝える API が無い | bank |
| A1-8 | `ICodec::Decode` のコメントに、吐き出しは終端を意味しないことと、保持の上限を明記する | codec |
| A1-9 | ハンドルのスロットの払い出しは `base::HandleAllocator`（ロックフリー、世代は 2^31 未満）で行うと明記する（A0-1 の解消） | base |
| A1-10 | RT スレッドのスタック量の下限（sinc リサンプラが比率 4 超で約 32 KiB を使う） | dsp |

実装で残っているもの:

| # | 内容 | 扱う段階 |
| --- | --- | --- |
| A1-11 | buildtool の ADPCM エンコードと DSP プール量の算出は差し込み口のまま。bank の IO は `IFileSystem` 直呼びのまま | 統合（段階2の前） |
| A1-12 | 各モジュールが `detail` に持った汎用部品（CRC-32C、ミューテックス、整列、LE の読み書きなど）を base に寄せる | 統合 |
| A1-13 | bank の検証器と buildtool の自己検査が、生成コピーで二重になっている（同期は ctest で検出） | 統合で、契約側の共有ヘッダにするかを決める |
| A1-14 | ワーカーがチャンクの番号を取った直後に止められると、そのチャンクは締切まで誰にも処理されない。待っている呼び出し側が代わりに処理できる | 段階2（core と一緒に） |
| A1-15 | 添字だけの `DecoderPool::Release` が残っている。Stream ソースでは世代つきの返却だけを使う | 段階2（source） |
| A1-16 | バンクをまたぐ行参照が無く、共有オブジェクトを使う側のバンクに複製している。core は ID で同一視する | 段階2（core） |
| A1-17 | セグメント入口のプリロード（開始フレームが 0 でないもの）をバンク形式で表現できない | 段階4（music） |
| A1-18 | プラグインエフェクトはサイドチェーンを受け取れない | 段階3 |
| A1-19 | Opus は未実装（A0-3）。入れる場合、デコーダのスロットは 32 KiB では足りない見込み | 方針の決定待ち |
