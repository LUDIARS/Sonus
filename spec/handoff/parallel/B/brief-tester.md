# セッション B: 独立テスト担当の決まり

受け入れ側（親セッション）が書いた。`brief-common.md`（同じディレクトリ）の §0〜§5 も全部読むこと。違うところはこの文書が優先。

## 立場

あなたは実装者とは別の担当。実装者のテスト（`core_*_test.cpp` など）は「実装者が自分で確かめた範囲」で、あなたの仕事は**仕様から見て壊れているところを見つけること**。直すのは実装者で、あなたは直さない。

## 手順（順番を守る）

1. **実装を読む前に**、仕様と公開ヘッダだけから「満たすべき性質」を書き出す。読んでよいもの:
   - `spec/architecture/design.md`（7 章の該当行、4 章、2.5、14 章など）、`spec/handoff/parallel/B-coverage.md` §2、`spec/interface/acceptance/stage3-coverage.md`
   - 公開ヘッダ（`contract/public/include/snd/*.h` / `*.hpp`）とそのコメント、`contract/internal/include/snd/internal/*.hpp`、`bank_format.hpp`、`spec/interface/bank-format.md`
   - 依頼文に書いた「決定」（D 番号）
   - `dsp/include/snd/dsp/*.hpp`（dsp の公開ヘッダ）
   - テスト基盤: `core/test/harness.hpp`、`core/test/test_bank.hpp`、`core/test/test_sources.hpp`、`core/test/indep_fixture.hpp`、`tests/framework/`
   - まだ読まないもの: `core/src/`、`dsp/src/`、実装者のテスト、実装者の報告
   書き出した一覧を、依頼文で指定した報告ファイルの先頭に「性質の一覧」として保存してから次へ進む。
2. その性質をテストにする。新しいファイル（`core/test/indep_<組>_*_test.cpp`、`dsp/test/indep_<組>_*_test.cpp`）だけを足す。`core/test/CMakeLists.txt` / `dsp/test/CMakeLists.txt` は末尾追記。既存のファイル（実装者のテスト、`test_bank.hpp`、`harness.hpp`）は変えない。足りない土台は自分のファイルの中に作る（`indep_fixture.hpp` の形にならう。バンクを自分で組み立ててよい）。
   - 音で確かめる（振幅、周波数、位相、時刻をサンプル単位で）。「落ちない」「呼べる」だけのテストにしない。
   - 境界: 0、最大、範囲外、NaN / 無限大、予算ちょうど・1 つ超え、ブロックの境目、同じブロックに複数の命令、順序の入れ替え、途中での停止・一時停止・仮想化・バンクの取り外し。
   - 決定論: 同じ台本を 2 回 → 同じビット。直列描画と並列描画（RT ワーカー 0 と 2）→ 同じビット。
   - 初期化後の確保ゼロ、RT 安全性の検出ゼロ（`CoreMemory` / `CoreRt` の形）。
   - variant 0 の振る舞いが従来どおりであること（予約欄に 0 を入れた命令で結果が変わらない）。知らない variant で落ちないこと。
3. ここで初めて実装（`core/src`、`dsp/src`）と実装者のテストを読み、**実装を知ったうえで壊れそうなところ**を追加で突く（列の所有者 D-18/D-35、D-43 の範囲、スロットの再利用、世代、フェード中の切り替え、プール枯渇、あふれ、整数の丸め、0 除算、未初期化、TSan の競合）。
4. 落ちたものを仕分ける:
   - **欠陥**: 仕様・公開ヘッダのコメント・決定と、実装が食い違う。テスト名を `Defect_` で始め、落ちる形のまま残す（`DISABLED` にしない、期待値を実装に合わせない）。
   - **仕様の穴**: 仕様にも決定にも答えが無い。テストにはせず（または現状を記録するだけの通るテストにして `SpecHole_` で始め）、報告に「どう決めるべきか、選択肢」を書く。
   - 自分のテストの誤りは直す。
5. 全部を回す: gcc Debug（全件）、ASan/UBSan、TSan（足したテストは `--repeat until-fail:20`、`-j1`）、Release（足したテストは `--repeat until-fail:20`）。`Defect_` 以外は全部通ること。`Defect_` で落ちるテストの名前と出力を報告に貼る。
6. ローカルコミット（push しない）。メッセージは日本語、末尾は brief-common.md §5 の 2 行。

## 報告（依頼文で指定したファイルと、最後の返事）

- 性質の一覧（手順 1。実装を読む前に書いたもの）と、性質 → テスト名の対応
- 欠陥の一覧（`Defect_` のテスト名、何が期待で何が出たか、原因の見立て。直し方は実装者が決めるので短く）
- 仕様の穴の一覧（選択肢と、あなたの勧め）
- 契約・公開ヘッダのコメントと実装の食い違い
- 確かめられなかったこと（理由つき）
- 構成ごとの結果（件数、通過、落ちた `Defect_` の名前）、ブランチの先頭のハッシュ
