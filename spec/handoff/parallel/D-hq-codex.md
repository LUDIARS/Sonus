## 3. 知っておく制約

1. **core は Granular と Patch に、今はパラメータを渡さない。** `core/src/sys_event.cpp` の SYNP の分岐は、この 2 種別を `params = nullptr` で `Start` する。`core/src/bank_registry.cpp` も `OscillatorParams` と `NoiseParams` しか作らない。core は B の持ち場なので変えない。
2. **buildtool はパッチを拒否する。** `buildtool/src/build.cpp` は `kind: patch` を「stage 6」のエラーにする。バンク形式の `PTCH` チャンクは名前だけあり、中身の形式は未定義（`bank-format.md` 「段階 6 で形式を定める」）。buildtool と形式の文書は C の持ち場なので変えない。
3. したがって、Granular と Patch は**種別の単位**（`ISourceKind` を直接駆動する）で完成させてテストする。core と buildtool への配線は、依頼として書く（H4）。core を通したテストは、core を変えずにできる範囲（`params == nullptr` の `Start` が落ちずに失敗を返す、など）だけにする。
4. **source は dsp に依存できない**（設計書 12.1）。パッチのフィルタなどは source の中に小さく持つ。
5. **新しいコマンド種別は足せない**（共通の決まり 4 章）。`snd_play_granular` のような公開 API が core のコマンドを要するなら、実装せずに依頼に書く。
6. ソース組 1 で `RenderItem` の末尾に `Ramp dutyOffset` / `tablePositionOffset` を足した（D-191）。core は `RenderItem{}` で 0 に初期化してから埋めるので、**末尾に足した欄は 0 が届く**。Granular / Patch の変調の欄も同じやり方で足せる（0 = 変調なし）。core が実際に値を入れる配線は依頼（D-01 と同じ形）。

## 4. 渡す作業と実装の条件

共通の条件（H1〜H4 のすべて）:

- `source_if.hpp` の冒頭の約束を守る。
  - ボイスごとの仮想呼び出しをしない。`RenderBatch` は種別ごとのループ。
  - RT で安全（ロック、確保、IO をしない。`rt_check.hpp` のフックが検出する）。
  - 初期化のあとに確保しない。プールは `PoolBytes` / `Init` で取り切る。
  - 遅れたチャンク（D-43）: `RenderBatch` が触ってよいのは、自分のチャンクの `RenderItem`、出力、スクラッチ、自分のボイスの状態だけ。`ScheduleBackground` は描画状態を書かない。
- `Start` / `Release` / `Control`（Seek、Pause、Resume、Virtualize、Devirtualize、SetLoop）/ `QueryReady` / `AdvanceVirtual` / `PrimeFrames` を全部実装する。種別ごとに各 op の扱いを決めて、決定に書く。
- 仮想の間も時間どおり進む。`AdvanceVirtual` の費用は O(1) かそれに近くし、仮想からの一斉復帰が RT のスパイクにならないようにする（ソース組 1 の Noise で実際に指摘された。D-199 (2)）。
- 決定論（設計書 2.5）: 乱数は `SourceStartRequest::seed` から作る。同じシードならビット一致。ブロックの切り方、バッチの中の並び、並列チャンクの割り当てに結果が依らない。
- NaN / Inf / 範囲外の入力（パラメータ、`RenderItem` の欄、プログラムの引数）で、落ちない、NaN を出さない、未定義動作を起こさない。
- 例外と RTTI なし、警告ゼロ（`-Werror`）、サードパーティ依存なし。コメントは英語、既存の書き方と `.clang-format` に合わせる。
- 最小の縦切りで止めない。設計書 5 章の該当する機能を全部、配線とテストまで入れる。

### H1: 決定 D-200 の仕上げ

ソース組 1 の再確認で出た 4 点への、受け入れ側の決定。実装し、`CONTRACTS.md` の「ソース組 1」の小節に D-200 として書き足す。関係する D-193 / D-197 / D-198 / D-199 の記述も、食い違わないよう直す。

1. **Noise の数値の訂正**: 1024 標本からの作り直しの直後の、連続に描いた場合との最大差は、実測でピンク約 8e-3、ブラウン約 1.6e-3（復帰した時点のフィルタの状態に依る）。D-199 の「ピンク 2e-3、ブラウン 7e-5」を直す。実装は変えない。
2. **Input のアンダーランの数え方**: 数えるのは「不足が始まった回数」（全部出していたブロックの次に不足したブロック）。不足が続く間の 2 ブロック目以降は数えない。`InputPortStats::underruns` などのコメントを合わせる。
3. **Oscillator の周波数 0 との行き来**: 段差を避けるため、実効の周波数が 0 になったら出力を 5 ms の線形のフェード（サンプル単位）で 0 へ下げ、正に戻ったら同じ長さで戻す。位相は止めて保つ（D-198 (1) のまま）。フェードの途中で向きが変わってよい。開始の時点で周波数が 0 のボイスは利得 0 から。ブロックの切り方に結果が依らない。
4. **Input のポートの容量の下限**: 容量は最低 4 ブロック（4 × `blockFrames`）に切り上げる。1 ブロック以下だと「今から」と遅延の上限（D-197 (2)(4)）が効かないため。

D-200 で落ちる独立テスト（`source/test/indep_*`）は、独立テストの担当（H5）が直す。実装の担当は書き換えない。落ちる見込みのもの:

- `IndepOsc.ExtremeFrequenciesAndRatiosStayFinite` と `ZeroFrequencyIsSilentAndKeepsThePhase`: レート比 0 で、すぐ 0 になることを期待している。
- `IndepInput.ThreadedWriterExactAccounting`: 容量 256（= 1 ブロック）のポートを前提にしている。

### H2: Granular（`SourceKind::Granular`、`GranularParams`）

- **素材**: Sample の波形（`GranularParams::asset`）。常駐 PCM を直接読む。圧縮やストリームの資産を拒否するか PCM キャッシュを使うかを決める。バンクの解放と素材の寿命は、Sample の種別（`sample_kind.*`、`pcm_cache.*`）と同じ扱いにする。
- **パラメータ**: グレインの長さ、密度（1 秒あたりのグレイン数）、位置（素材の中の読み出し位置）、ばらつき（位置とピッチ。設計書の表は「密度、長さ、位置、ピッチ揺らぎ」）、窓、ピッチ（`RenderItem::pitch` との関係を決める）。
- **窓**: ハン、三角、矩形のほか、要るものを選ぶ。重ね合わせの和が平らになる条件（密度 × 長さと窓の種類の関係）を、数式で決定に書く。
- **固定容量のグレインのプール**: ボイスあたりの最大グレイン数と、全体の上限。足りないときの扱い（新しいグレインを出さない、またはいちばん古いものを切る）を決める。
- **レート**: 出力レートの種別か元のレートの種別か（`RendersAtOutputRate()`）を決める。素材のレートと内部レートの違い、補間の方式（線形か 3 次か）、素材とボイスのチャンネル数の違いの扱いを決める。
- **位置の意味**: 固定か、時間で進む（スキャン）か。ループ点の扱い、素材の端をまたぐグレインの扱い。
- **契約**: `GranularParams` に無いパラメータ（窓の種類、位置のばらつき、スキャンの速度など）は、構造体の**末尾への欄の追加**で足す。0 が既定の挙動になるようにし、既存の欄の意味は変えない。
- **Parameter で動かす経路**: 密度、長さ、位置、ピッチ揺らぎを実行時に変えるための欄を、`RenderItem` の末尾に足す（0 = 変調なし）。core の配線は依頼に書く。
- 密度とグレイン数の関係、窓の和、位置の範囲を、テストで解析的に確かめられるよう、数式で決定に書く。

### H3: Patch（`SourceKind::Patch`、`PatchParams`）

設計書 5 章「ツールで組む小さな合成グラフ（Osc → Filter → Env 等）、ノード上限あり」と 5.1 に従う。

- **PTCH の形式を定める**: バイト列の仕様（版、ノードの数、ノードの種類と引数と入力の結線、出力ノード。リトルエンディアン、アラインメント、上限）。
- **ノードの種類**: 必要十分な集合を決める。案:
  - オシレーター（ソース組 1 の波形の実装を共有する。PolyBLEP）、ノイズ、定数
  - ゲイン / 乗算、加算 / ミキサー
  - フィルタ（1 極、または 2 極の SVF か biquad。source の中に持つ）
  - ADSR、LFO、ランダム（サンプル＆ホールド）
  - 波形整形（tanh、クリップ）、出力
- **循環の禁止**: 形式の上で「ノードは依存順に並ぶ（入力は自分より前のノードだけ）」を要求する。実行時は配列を前から順に評価する小さなインタープリタにする。これが「評価順が決定的」の根拠になる。
- **検証**: 壊れたプログラム（範囲外の結線、循環、ノード数の超過、未知の種類、短いバイト列、NaN の引数）は、鳴らさずに失敗を返す。落ちない、範囲外を読まない、ファズに耐える。`Start` の中で検証するなら、確保なしで RT に収まる費用（ノード上限が小さければ O(N)）にする。重い検査を読み込み時に置くなら、その分は依頼に書く。
- **モジュレータ**: ADSR や LFO はブロック単位で評価し、サンプル単位の線形補間でジッパーノイズを防ぐ（5.1）。ただし結果がブロックの切り方に依らないよう、評価の刻みを固定のサンプル数（ボイスの開始からの絶対位置で、例 32 サンプルごと）にする。刻みを決定に書く。
- **状態と中間バッファ**: ボイスごとの状態（位相、フィルタ、エンベロープの段階、乱数）は固定容量のプール。中間バッファは `RenderBatch::scratch` から取る。足りなければ無音にして starved を報告する（`source_if.hpp` の `Scratch::Take` のコメント）。
- **エンベロープの終わり**: `Release` は即解放なので、ノートオフの伝え方と、core の「止める」のフェードとの関係を決める。ADSR が終わったらボイスを `ended` にするかを決める。
- **ピッチ**: `RenderItem::pitch` をパッチの中のオシレーターの周波数に掛ける。
- **組み立ての API**: `source/include/snd/source/patch_program.hpp` のようなモジュールの公開ヘッダに、プログラムを組み立てて PTCH のバイト列にするビルダー（確保なし、呼び出し側のバッファに書く）と、検証の関数を置く。テストはこれでパッチを組む。buildtool は将来これを呼ぶか、同じ形式を出す。

## 5. 進め方

### 5.1 役割

共通の決まり 3 章のとおり、**実装と独立テストは別のセッションにする**。同じ Codex のセッションに両方をさせない。

- **実装**: Codex のセッション 1 つ。H1 → H2 → H3 → H4 の順。
- **独立テスト**: 実装とは別の Codex のセッション。実装の会話を引き継がせない。
- **受け入れ**: 本社の担当者（または 3 つ目のセッション）。決定を下し、全構成を新しいビルドディレクトリから回し、要所のコードを読む。

### 5.2 1 つの組の流れ

1. **実装する**。区切りごとにコミットして `int/s7-ext-src2` に push する。未検証の箇所を隠さず報告させる。
2. **独立テストを付ける**。担当は次の順を守る。
   1. 実装を読む**前に**、仕様（設計書、`CONTRACTS.md` の決定、公開ヘッダ、契約ヘッダ）だけから、満たすべき性質を書き出す。
   2. そのあとで実装と実装者のテストを読み、見ていない性質、甘い許容差、机上で見つかる欠陥を探す。
   3. 新しいテストファイルだけを足す（`source/test/indep_*`）。期待値の計算は自分で持ち、実装の関数を期待値に使わない。
   4. 欠陥は、失敗する `Defect_` のテストとして別の実行ファイル（`indep_defects_src2_test.cpp`）に残し、**直さない**。仕様が曖昧なものは「仕様の穴」として欠陥と分ける。

### 6.2 H1（D-200）で確かめること

- 周波数 0 との行き来: 利得が 5 ms の線形で動く。途中で向きが変わっても連続。位相は保たれる。開始時に周波数 0 のボイスは無音から。隣のサンプルとの差の上限（段差が無いこと）を、波形の最大の傾きから導いた値で検査する。ブロックの切り方を変えてもビット一致。
- ポートの容量: 4 ブロック未満の指定が 4 ブロックになる。そのとき「今から」（最新の 1 ブロックを残す）と遅延の上限（下限 2 ブロック）が実際に効く。
- アンダーランの統計が「不足が始まった回数」になっている。
- D-197〜D-199 の既存のテストが通り続ける。

### 6.3 H2（Granular）で確かめること

解析的に期待値が分かる検査にする（`D-extensions.md` 3 章）。

- **密度とグレイン数**: 決定の式どおりの数のグレインが出る。長い時間で誤差が溜まらない。
- **窓の和**: 重ね合わせが平らになる条件（決定の式）で、直流の素材に対して出力が定数になる。許容差を明示する。
- **位置の範囲**: 読み出しが、決めた範囲から出ない。素材の端、ループ点、長さ 0 や 1 フレームの素材。範囲外を読まないことを ASan でも確かめる（素材と同じ大きさのバッファを使う）。
- **ピッチ**: 正弦波の素材で、グレインのピッチを変えたときの周波数（DFT のピーク）。ピッチ揺らぎの分布の幅。
- **決定論**: 同じシードでビット一致、違うシードで違う。ブロックの切り方、バッチの中の並び順、チャンクの割り当てに依らない。
- **プール**: 上限を超える密度での扱いが決定どおり。Release したスロットを再利用しても前の状態が漏れない。
- **仮想**: 仮想の間もグレインの発生列が時間どおり進む。仮想から戻ったときに、連続に描いた場合と一致する（または決定に書いた差に収まる）。
- **制御**: Seek、Pause、Resume、SetLoop の扱いが決定どおり。
- **入力の頑健さ**: NaN / Inf / 負 / 0 のパラメータ、素材の無い `Start`、`params == nullptr`、圧縮やストリームの資産。

### 6.4 H3（Patch）で確かめること

- **小さなグラフ**: オシレーター → ゲイン → 出力 で、期待どおりの波形になる（ソース組 1 の Oscillator の理論のフーリエ係数 × ゲイン）。
- **評価順が決定的**: 同じプログラムと同じシードで 2 回描いてビット一致。ブロックの切り方に依らない。依存順でないプログラムは検証で弾かれる。
- **ノードごとの解析的な検査**: フィルタの周波数応答を解析式と比べる。ADSR の形（各段の時間とレベル）。LFO の周波数。加算と乗算。波形整形の伝達関数。
- **モジュレータの刻み**: 決めた刻みで評価され、その間が線形に補間される。刻みの境目に段差が無い。
- **検証とファズ**: 壊れたプログラム（切り詰め、範囲外の結線、循環、ノード数の超過、未知の種類、NaN の引数、巨大な値）を大量に与えても、落ちない、範囲外を読まない（ASan / UBSan）、鳴らさずに失敗を返す。ビルダーが作ったプログラムは必ず検証を通る。
- **スクラッチ不足**: `RenderBatch::scratch` が足りないとき、無音と starved になり、落ちない。
- **エンベロープの終わりと `ended`**、ピッチ、仮想、制御の扱いが決定どおり。

### 6.5 共通で確かめること

- **RT 安全性と負荷**: 各種別を上限の本数（`maxVoices`、実ボイスの上限）で鳴らし、初期化のあとの確保ゼロ、RT 安全性の検出ゼロ（`rt_check`）。上限より多い `Start` の失敗の返し方。
- **処理時間**: Release で、128 本のステレオを 1 バッチ、256 フレーム（48 kHz、予算 5333 µs）あたりの時間を測って報告に書く。Granular は密度ごと。仮想からの一斉復帰のブロックの時間も測る。参考（ソース組 1）: Oscillator 約 250 µs、Noise 約 540〜600 µs、Input 約 13 µs。
- **遅れたチャンク（D-43）**: 別のスレッドの `RenderBatch` と、オーディオスレッドの操作（`Start` / `Release` / `Control` / `ScheduleBackground`）の同時実行で、TSan の検出が無い。並行部分はコードを読んで机上でも検証し、結論を報告に書く。

- **設計書 7 章との対応**: 「動的生成・入力」の行に、ソース組 2 のテストが対応している。

## 8. クラウドに残す作業（参考: dsp 組の差し戻し）

本社が dsp も引き取る場合は、この章が出発点になる。その場合は先に知らせてほしい（同じファイルを 2 者が直さないため）。

独立テストで見つかったもの。`Defect_` のテストは `dsp/test/indep_defects_dsp_test.cpp` にある。

| # | 重さ | 内容 | 場所 |
| --- | --- | --- | --- |
| 1 | 低 | タイムストレッチ: `maxSpeed` に NaN を渡すと 4 として扱う（D-210 は 1） | `dsp/src/time_stretch.cpp` の `Shape` と `Init` |
| 2 | 高 | タイムストレッチ: 逆相のステレオ（R = −L）で探索が働かない。全チャンネルの和で相関を取るので和が 0 になり、常に探索範囲の端を選ぶ | `time_stretch.cpp` の相関の計算 |
| 3 | 中 | コンボリューション: IR の切り替えで、FFT の部分が 1 分割（最大 B フレーム）遅れて古い IR のまま出る。その間、新しい IR の先頭と古い IR の後ろが混ざる | `dsp/src/fx_convolution.cpp` の `Step` と `ConvolutionProcess` |
| 4 | 中 | コンボリューション: `max_frames` より長い呼び出しで `IrSlot` がサブブロックごとに補間され、途中の番号の IR が鳴る | `dsp/src/effects.cpp` の `ProcessCore` |

仕様の穴と設計への異議（決定が要るもの）:

- IR の登録表がプロセスに 1 つで、枠に所有者も世代番号も無い。複数の `snd_system` があると、解放後の IR を参照しうる。`IrSlot` はライブリンクやスナップショットで書けるので、他のバンクの IR を指せる。
- `EffectReset` と NaN からの回復が、状態の全体（MB 単位）を memset し、FFT の計画（三角関数）も作り直す。
- IR の切り替えにクロスフェードが無い。
- IR の準備で、NaN / Inf のサンプルを拒否しない。
- WSOLA は過渡を崩す（クリック列が速度 0.5 で全部 2 重、速度 2 で 3 分の 1 が消える）。D-209 の「過渡を崩さない」という理由づけと合わない。
- 50 Hz では探索幅（±8 ms）が 1 周期に届かず、歪みが約 −12 dB 出る。
- 速度のランプの端点に ±Inf を渡すと、そのブロックが速度 1 になる。
- 遅延 0 のとき、実際に使う IR の長さが、申告した容量より 1 分割長い（害は無い。記述の食い違い）。
- ヘッダのコメントの誤記 2 件（`convolution.hpp` の IR のレート変換の説明、`effects.hpp` の `EffectLatencyFrames`）。
