# C-20: ツールの中でランタイムを組み立てる口（依頼先: api / 統合担当）

## 何が要るか

プレビューエンジン（`tool/preview/`、組 P）は、ゲームと同じランタイム（ファイルシステム、ワーカー、コーデック、IO とストリーム、
ソースの種別、音楽、core、ライブリンク）をツールのプロセスの中で組み立てる。今は `api/compose/compose.cpp`（D-93）と
同じ順序をツールの側で組み直している（`tool/preview/src/runtime_host.cpp`）。次のどちらかがあれば、それを使って二重の
組み立てをやめられる。

1. 構成ルートの内部の入口（`snd/api/compose.hpp`、C++ だけ、公開しない）:

   ```cpp
   struct ComposeHooks {
     livelink::IAcceptor* liveAcceptor = nullptr;   // ライブリンクをこの転送路で（TCP の代わり）
     livelink::Replayer* replayer = nullptr;        // LiveRuntime の代わりに Replayer を CoreDesc に入れる
     livelink::IStructEditor* structEditor = nullptr;
     bool manualRender = false;                     // デバイスを開かず、呼び出し側が RenderBlock する
   };
   snd_result ComposeWith(const snd_config* cfg, const snd_allocator*, const snd_file_system*, const ComposeHooks&,
                          snd_system** out);
   void RenderBlocks(snd_system*, std::uint32_t blocks, float* out);  // manualRender のとき
   ```

2. または C API の追加（契約の minor）: `snd_config` の末尾に「ライブリンクの転送路をプロセス内にする」選択と、
   `snd_live_connector(sys)` のような接続口。Replayer を入れる口は C API では難しいので、1 の方が素直。

## なぜ

- D-93 の作る順・壊す順、D-95 の出力の橋渡し、D-97 のコールバックの預かりなどを、ツールの側で写すと食い違う。
- C API（`Sonus::sonus`）はライブリンクを TCP（`Config.livelink.port`、ポートを返す関数なし）でしか起こさず、
  Replayer を入れる口も無い。

## それまでの回避

`tool/preview/src/runtime_host.cpp` が `compose::SourceKinds`（api の公開ヘッダ）と各モジュールを直接使って組み立てる
（作る順は D-93 と同じ）。出力の橋渡しはチャンネル数を core に合わせて開くので、D-95 の写しは簡単な形だけ。
フォーカス・サスペンド・アンダーランの追い付きの扱いはデバイス出力のときだけ（D-95 の一部を写した）。

## つないでいない箇所

- `snd_set_callbacks` 相当（on_end など）はプレビューでは使っていない（試聴の終わりは `GetPlaybackState` で見る）。
- `jobs.external`、プラグインのコーデック・エフェクトの表はプレビューでは渡していない。
