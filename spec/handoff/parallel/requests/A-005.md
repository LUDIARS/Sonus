# A-005: suspend 中にコマンドを記録し続けると `snd_resume` が通らなくなる（core への依頼）

- 依頼元: セッション A（physics）
- 宛先: core の所有者（コマンドの記録と適用、suspend / resume）
- core の対応: 各アリーナに停止・再開用の 8 バイトを確保し、通常の予約領域が使えないときは同一アリーナの最終要求を保持する。D-125 は停止中の接触記録を抑えるために引き続き使う。

## 修正前の挙動

`snd_suspend` の後、ゲームが毎フレーム、コマンドを記録して `snd_update` を呼び続けると、`snd_resume` が
`SND_ERR_COMMAND_BUFFER_FULL` を返し、`snd_update` を挟んで何度やり直しても通らない。系を再開できなくなる。

修正前の `sonus.h` は `snd_suspend` / `snd_resume` を「Recorded like other commands」とだけ書いていて、再開できなくなる
場合があるとは書いていない。

修正前の再現（公開 API だけ。`physics/test/indep_final_test.cpp` の
`IndepFinal.CoreA005_ResumeRefusedAfterRecordingWhileSuspended`）:

1. `snd_suspend`。
2. 2000 フレームのあいだ、毎フレーム `snd_set_param_global` を 64 件記録して `snd_update`。
3. `snd_resume` → `SND_ERR_COMMAND_BUFFER_FULL`。`snd_update` と `snd_resume` を 100 回繰り返しても通らない。

確かめたこと:

- 何も記録しなければ、4000 フレーム後でも再開できる。
- 300 フレームでは、Release で 20 回のうち 7 回は再開できた（量と時間に依る）。
- 出力を進めないだけ（suspend しない）の場合は、記録が拒否されるが、出力が進めば回復する。

## 当初の依頼

どれかにしてほしい。

- `snd_resume`（と `snd_suspend`）は、コマンドの領域が満杯でも必ず受け付ける（必ず届ける種類の予備を持つ）。
- suspend 中に記録されたコマンドを、溜めずに捨てるか、最新の値だけにまとめる。
- どちらもしないなら、`sonus.h` に「suspend 中はコマンドを記録しない」という利用者の義務を書く。

## physics 側の対応（D-125）

`snd_phys_submit_contacts` のたびに `snd_get_stats` の `block_index` を読み、進んでいない呼び出しが `stall_calls`
（既定 64）回続いたら、音声側が止まっているとみなして記録をやめる（衝突は捨てて `dropped_audio_stalled`、
擦れ音は値だけ持って再開後に反映）。`snd_phys_play_footstep` と `snd_physics_play_at` はゲームが直接呼ぶものなので、
止めていない。

## 回帰テスト

- `IndepFinal.CoreA005_ResumeSurvivesSuspendedFlood` は上記の負荷で最初の `snd_resume` が成功し、手動出力を進めた後に共通時計が進むことを検査する。
- `IndepStall.CoreA005_FootstepsAndPlayAtWhileSuspended` は、足音と PlayAt を各 2000 回要求した後に再開でき、新しく右側で鳴らした音が右チャンネルから出ることを検査する。
