# D-room-portal: ルーム／ポータル（部屋と開口部による伝搬）の設計メモ

- 出した側: セッション D（段階6 拡張）
- 宛先: 統合担当、core の担当（B の段階3 が統合されたあとの別の組）、C（buildtool / tool）
- 状態: **設計メモだけ**。実装していない。D-extensions.md 1 章の「作らないもの」に当たる。
- 根拠: 設計書 4.5（3D と空間）、7 章「範囲・空間構造」の行（判定は近似。ルーム／ポータルは段階6）、15.1 の段階6。

このメモは、B の段階3（3D、リバーブゾーン、範囲音源、距離カーブ）が入った `int/s2-integration` を土台にする前提で書いた。
段階3 の実装で名前や列が変わっていたら、そちらに合わせる。

## 1. 何を作るか

部屋（ルーム）と、部屋どうしをつなぐ開口部（ポータル）のグラフを使い、次の 3 つを出す。

1. **回り込み**: 音源とリスナーが別の部屋にいるとき、音は直線ではなくポータルを通って届く。見かけの方向はポータルの方向、距離は経路の長さにする。
2. **遮り**: ポータルの開き具合（ドアの開閉、0〜1）と、部屋の壁の透過損失で、音量とローパスを決める。
3. **部屋の響き**: 音源は「自分のいる部屋」のリバーブバスへ送り、リスナーは「自分のいる部屋」と、ポータルで隣り合う部屋の響きを、ポータルの方向から聞く。

作らないもの（このメモの範囲の外）:

- 形状からの自動計算（レイキャスト、ジオメトリの回折、反射の経路探索）。設計書 4.5 のとおり、レイキャストはゲーム側のまま。
- HRTF とアンビソニックス（15.2 の未決事項）。

## 2. データ

### 2.1 置き場所

| 物 | 寿命 | 置き場所の案 |
| --- | --- | --- |
| 部屋の定義（形、響きの設定、壁の透過損失） | レベルと同じ | バンクの新しいチャンク（`ROOM`）。実行時に登録する API も用意する |
| ポータルの定義（つなぐ 2 部屋、位置、大きさ） | レベルと同じ | バンクの新しいチャンク（`PRTL`）。実行時の登録も可 |
| ポータルの開き具合 | ゲームが毎フレーム変える | Parameter（グローバル、ポータルごとに 1 つ）。新しいコマンド種別は要らない |
| 音源とリスナーのいる部屋 | 位置から決まる | core が Compute3D で求める。ゲームが上書きもできる（Emitter の Parameter） |

- 部屋の形は**凸の箱（向きつき、OBB）**だけにする。任意のメッシュは扱わない。入れ子と重なりは優先度の数値で解く。どの部屋にも入らない位置は「屋外」（部屋 0）とする。
- ポータルは**向きつきの矩形**（中心、法線、幅、高さ）。つなぐ部屋は 2 つ（片方は屋外でもよい）。
- 上限は `snd_config` の末尾に足す: `max_rooms`（既定 64）、`max_portals`（既定 128）、`max_portal_hops`（既定 2、最大 4）。テーブルは Create で確保し、あとで確保しない。

### 2.2 テーブル（schema への追加の案）

| 表 | 種類 | 所有 | 列 |
| --- | --- | --- | --- |
| `Room` | Direct | ApplyCommands | 中心、軸 3 本、半分の大きさ、優先度、リバーブのバス ID、壁の透過損失（dB）、壁のローパス（Hz）、有効 |
| `Portal` | Direct | ApplyCommands（開き具合だけ EvaluateLogicParams） | 部屋 A、部屋 B、中心、法線、幅、高さ、開き具合、閉じたときの損失（dB）とローパス |
| `RoomPath` | Direct（`maxRooms × maxListeners`） | Compute3D | リスナーの部屋から各部屋への、最短経路の最初のポータル、経路の長さ、通るポータルの数、開き具合の積 |

- `Emitter` と `Listener` に、いる部屋の列（`roomSlot`、Compute3D が所有）を足す。
- `Spatial` に、回り込みのあとの見かけの方向・距離・遮りの量を足す。ボイスは今までどおり `Spatial` を参照するだけにする（4.5 の「計算は Emitter × Listener の組ごとに 1 回」を保つ）。

## 3. 計算（Compute3D の中）

ブロックごとに、次の順で行う。どれも直列の部分で、確保はしない。

1. **部屋の判定**: Emitter とリスナーごとに、位置がどの箱に入るかを調べる。前のブロックの部屋から先に調べ、境界のちらつきを防ぐため、出るときは少し余裕（ヒステリシス、既定 0.25 m）を持たせる。Emitter の数 × 部屋の数になるので、部屋を一様格子に入れておき、調べる数を減らす。
2. **経路**: リスナーの部屋を始点に、ポータルのグラフを幅優先でたどる（深さは `max_portal_hops` まで）。各部屋について、最短の経路の「リスナーから見て最初のポータル」と経路の長さを `RoomPath` に書く。計算量は 部屋 + ポータル に比例し、リスナーごとに 1 回で済む。
3. **Emitter ごとの結果**:
   - 同じ部屋: 今までどおりの直線。
   - 経路がある: 見かけの方向 = 最初のポータルの上で、音源への直線にいちばん近い点の方向。見かけの距離 = 経路の長さ（ポータルの中心を結んだ折れ線。両端は実際の位置）。音量 = 距離カーブ（見かけの距離）× 開き具合の積 × 曲がる角度による回折の損失（角度のカーブ、既定は 90 度で −6 dB とローパス 2 kHz）。
   - 経路が無い（深さの上限を超えた、または全部閉じている）: 壁越しの透過だけ。方向は直線、音量は壁の透過損失、ローパスは壁の値。
   - 経路と透過の両方があるときは、音量の大きい方を使う（エネルギーの和にはしない。ボイスを 2 つに分けないため）。
4. **補間**: 部屋が変わった瞬間に方向と音量が飛ばないよう、`Spatial` の結果は既存のブロック間の線形補間に加えて、切り替えのとき 50 ms（仮）のクロスフェードをかける。

遮蔽・閉塞（ゲームから渡す Parameter、4.5）とは掛け合わせる。ルーム／ポータルは粗い伝搬、レイキャストは細かい遮蔽、という分担にする。

## 4. 響き（バスの配線）

- 部屋ごとにリバーブのバスを 1 つ持てる（部屋の定義がバスの ID を指す。同じバスを複数の部屋で共有してよい）。
- 音源は、自分のいる部屋のバスへセンドする。センド量は距離カーブの「リバーブセンド量」に従う。部屋が変わるときは、古いバスと新しいバスへのセンドを 50 ms でクロスフェードする。
- リスナーが別の部屋にいるとき、その部屋のリバーブバスの出力は、経路の最初のポータルの位置に置いた音源としてパンし、開き具合と経路の長さで絞る。これには「バスの出力を 3D でパンする」機能が要る（バスに位置を持たせる）。段階3 のリバーブゾーンの実装がバスのセンド量だけを動かす形なら、ここが新しい作業になる。
- コンボリューション（`snd.fx.convolution`、D-211〜D-215）を部屋のバスに置けば、部屋ごとの IR の響きになる。IR の切り替えはバスの切り替えで表す（1 つのインスタンスの IR を差し替えない）。

## 5. 公開 API の案（追加だけ）

```c
/* 実行時の登録（バンクに入れない場合）。Thread: registered. */
SND_API snd_room_handle   SND_CALL snd_create_room(snd_system*, const snd_room_desc*);
SND_API snd_result        SND_CALL snd_destroy_room(snd_system*, snd_room_handle);
SND_API snd_portal_handle SND_CALL snd_create_portal(snd_system*, const snd_portal_desc*);
SND_API snd_result        SND_CALL snd_destroy_portal(snd_system*, snd_portal_handle);
/* 開き具合 0（閉）〜1（開）。 */
SND_API snd_result SND_CALL snd_set_portal_openness(snd_system*, snd_portal_handle, float openness, float fade_seconds);
/* ゲームが部屋を知っているときの上書き。SND_ROOM_AUTO で自動に戻す。 */
SND_API snd_result SND_CALL snd_set_emitter_room(snd_system*, snd_emitter_handle, snd_room_handle);
SND_API snd_result SND_CALL snd_set_listener_room(snd_system*, uint32_t listener, snd_room_handle);
```

- コマンド種別は増やさずに済ませたい。登録と破棄は、既存の「オブジェクトの生成・破棄」のコマンドの `variant` で表せるかを、core の担当が確かめる。表せないなら、契約 1.3 のまとめの中で種別を足す（統合担当の判断）。
- 開き具合は Parameter に載せれば、スナップショット、ライブリンクの上書き、記録と再生がそのまま使える。

## 6. バンクとツール（C への依頼になる部分）

- プロジェクト形式: レベルごとの「空間」の定義（部屋の箱、ポータル、部屋とバスの対応）。buildtool が `ROOM` / `PRTL` のチャンクにする。バンク形式は 2.1 の追加になる。
- ツール: 上から見た図で部屋とポータルを置く画面までは要らない。ゲームエンジンのエディタから書き出す前提で、ツールは一覧と数値の編集、ライブリンクで「いまリスナーと各音源がどの部屋にいるか、どのポータルを通っているか」を見せるだけにする。
- ライブリンク: プロファイラの送信に、Emitter ごとの部屋と経路（最初のポータル、通る数）を足す。

## 7. テスト（解析的に期待値が分かるもの）

- 部屋の判定: 箱の内外、境界のヒステリシス、入れ子の優先度、屋外。
- 経路: 2 部屋 1 ポータルで、見かけの方向がポータルの方向になり、見かけの距離が折れ線の長さになる。3 部屋で最短の経路を選ぶ。深さの上限。閉じたポータルを避ける。
- 音量: 開き具合 0 → 透過だけ、1 → 回り込み。途中は単調に変わる。出力のパン（L/R の比）と音量を、式から求めた値と比べる。
- 連続性: 音源がポータルを通り抜けるとき、出力の音量と方向が飛ばない（隣のブロックとの差の上限）。
- 響き: 部屋を移ると、センド先のバスのメータが入れ替わる。別の部屋の響きがポータルの方向から聞こえる。
- 負荷: 部屋 64、ポータル 128、Emitter 上限、リスナー 4 で、Compute3D の時間を測る。確保ゼロ。
- 決定論: 同じコマンド記録で、部屋の判定と経路が一致する（2.5）。

## 8. 決めていないこと（実装の組で決める）

- 回折の損失のカーブの既定値と、ゲームが差し替える方法。
- 複数リスナーの合成方式（4.5 の 3 つ）それぞれでの `RoomPath` の扱い。「リスナー別の出力」では、リスナーごとに別のパンが要る。
- 範囲音源（線・面・箱）が部屋をまたぐときの扱い。
- バスの出力を 3D でパンする機能を、バスグラフのどこに入れるか（4 章）。
- 部屋の形を箱だけにする制限で足りるか（L 字の部屋は箱 2 つ + 開いたポータルで表す想定）。
