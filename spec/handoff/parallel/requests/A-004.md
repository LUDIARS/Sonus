# A-004: Emitter を同じまとまりで作成・移動・破棄すると位置が効かない／PlayAt の暗黙の Emitter（core への依頼）

- 依頼元: セッション A（physics）
- 宛先: core の所有者（`core/src/sys_apply.cpp`、`core/src/sys_3d.cpp`）
- 状態: 未着手。physics は回避策（音声側が再生を適用したのを見届けるまで Emitter を保持）で動いている。

## 1. 欠陥: 「再生は最後の transform を保つ」が成り立たない場合がある

`sonus.h` の `snd_destroy_emitter` のコメントは「Playbacks on the emitter keep the last transform」。
ところが、同じフレーム（同じ ApplyCommands）で

```
e = snd_create_emitter(sys);
snd_set_transform(sys, e, &(snd_vec3){2, 0, 0}, NULL, NULL);
snd_play(sys, event3D, e, NULL);
snd_destroy_emitter(sys, e);
snd_update(sys);
```

とすると、再生はリスナーの位置（中央、距離減衰なし）で鳴る。

確かめた結果（`SND_OUTPUT_MANUAL`、DC 0.5 のモノラル素材、3D の Event、リスナーは原点で前 (0,0,1)・上 (0,1,0)、
Emitter は右 2 m。期待は L ≈ 0、R ≈ 0.25）:

| 手順 | L | R |
| --- | --- | --- |
| 作成・移動・再生（破棄しない） | 0.000 | 0.250 |
| 作成・移動・再生・破棄を同じフレーム | 0.354 | 0.354（中央・減衰なし） |
| 作成・移動の後に 1 周期進めてから、再生・破棄 | 0.000 | 0.250 |
| `snd_play_at`（右 2 m） | 0.000 | 0.250 |

独立テスト（`physics/test/indep_play_test.cpp`、公開 API だけ）でも同じ数値で再現した（L 0.354 / R 0.354）。

原因（読んだ範囲）: `Compute3D`（`sys_3d.cpp`）は生きている Emitter の行についてだけ `Spatial` を計算する。
`DestroyEmitter` は ApplyCommands の中で行を消すので、そのブロックで作られた Emitter は一度も `Spatial` が
計算されず、ボイスは無効な 3D 値（2D 扱い）で鳴る。前のブロックで計算済みなら、その値が残るので正しく鳴る。

直し方の案:
- `DestroyEmitter` で、その Emitter を参照する Playback があれば、行を消す前にその Emitter の `Spatial` を計算する
  （`Compute3D` の 1 行分を呼ぶ）。または
- 破棄を「そのブロックの Compute3D の後」にずらす（破棄のビットを立てて、Compute3D の後に消す）。

## 2. 振る舞いの確認: `snd_play_at` の暗黙の Emitter は利用者の Emitter と同じプールから取る

`CreatePlayback`（`sys_apply.cpp`）は `kPlayHasPosition` のとき `im.emitterSlots.Acquire()` で暗黙の Emitter を取る。
`max_emitters` を使い切っていると、位置なし（リスナーの位置）で鳴り、何も通知されない。そのため physics は、
Emitter が取れないときに `snd_play_at` へ落とすのをやめた（3 節）。

依頼: どちらかにしてほしい。
- 暗黙の Emitter 用の予備（`Config` の容量）を持つ。
- 取れなかったことを `on_error`（警告）か終了理由の detail で知らせ、`sonus.h` のコメントに書く。

## 3. physics 側の対応

いまの physics は、単発の Emitter を保持し、`snd_get_playback_state` が NONE でなくなる（その再生を適用したブロックの
スナップショットが見える）か、ハンドルが古くなった（終わった）のを確かめてから、後の `snd_phys_submit_contacts` で
破棄する（物理の時刻には依らない）。Emitter が取れないときは `snd_play_at` に落とさず、その組を捨てる
（`dropped_no_emitter`。2 のため、`snd_play_at` もリスナーの位置で鳴ってしまうので）。

1 が直ったら、physics は再生の直後に Emitter を破棄でき、保持の環（`max_held_emitters`）と、そのための
問い合わせ（状態が NONE のあいだの音量の記録）が要らなくなる。A-002 が入れば Emitter 自体を使わない。

## 4. 追記（再確認で分かったこと）: 前のブロックから生きている Emitter でも起きる

1 節の表の 3 行目（「作成・移動の後に 1 周期進めてから、再生・破棄」は正しく鳴る）は、いつも成り立つわけではない。
独立テストの記録（`physics/test/indep_play_test.cpp` の `IndepPlay.CoreA004_EmitterCreatedAndDestroyedInOneUpdate`、
公開 API だけ）では、前の周期から生きている Emitter で `snd_play` と `snd_destroy_emitter` を同じまとまりで
呼ぶと、Release 構成の 40 回のうち 5〜9 回がリスナーの位置で鳴った（Debug では再現していない）。
「再生は最後の transform を保つ」は、再生の記録と破棄の記録が同じまとまりにあるかぎり、当てにできない。

physics の今の規則（再生そのものが適用されたのを見てから、後の呼び出しで破棄する）は、この場合も避けている。

## 5. 追記: Emitter を破棄した後に始まる子の再生は、位置を引き継がない

Event のアクション（`timeMs` 100 の `play`）が入れ子の 3D の Event を鳴らす場合、親の再生が適用された後に Emitter を
破棄すると、後から始まる子の再生はリスナーの位置（中央、減衰なし）で鳴る。

確かめた結果（`physics/test/indep_recheck_test.cpp` の `IndepRecheck.CoreNestedPlayAfterEmitterDestroyed`、公開 API だけ。
Emitter は右 2 m）:

| 手順 | L | R |
| --- | --- | --- |
| Emitter を保ったまま | 0 | 3904 |
| 親の再生の 3 フレーム後に Emitter を破棄 | 5521 | 5521（中央・減衰なし） |

遅れて始まるクリップ（`startMs` 100）と、プライミングのあるストリームは位置を保つ（同じファイルの
`LateStartingVoicesKeepThePosition`）。失うのは、アクションが後から作る子の再生だけ。

`sonus.h` の「Playbacks on the emitter keep the last transform」を、子の再生にも及ぶと読むなら core の欠陥。
及ばないと読むなら、その旨を `sonus.h` に書いてほしい。

依頼: 親の再生が持っている最後の transform（計算済みの 3D の値）を、アクションが作る子の再生が引き継ぐようにする。

physics 側の扱い: 規則は変えない（子の再生が終わるまで Emitter を持ち続けると、音の長さのぶんだけ Emitter を
占有し、ゲームの Emitter を枯らす）。対応表に登録する Event が、時間をおいて入れ子の Event を鳴らすアクションを
持つ場合、その子の音は位置を失う、と `physics.h` に書く。スティンガーや音楽の子の再生では確かめていない。
