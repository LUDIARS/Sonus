## 3. 役割と手順（段階1で使ったもの。同じ手順で続ける）

役割:

- **実装**: Opus のエージェント。モジュール（または依存でまとまる組）ごとに 1 体。別々の git worktree で並列に動かす。
- **テスト**: Opus のエージェント。実装者とは別の 1 体を組ごとに付ける。
- **受け入れチェック**: Fable（親のセッション自身）。

1 つの組の流れ:

1. 実装担当に依頼する。触ってよいディレクトリ、凍結ファイルに触らないこと、完了条件（下の「ビルド構成」）、ローカルコミットだけで push しないこと、未検証の箇所を隠さず報告することを書く。
2. 実装が終わったら、同じ worktree に独立テスト担当を付ける。依頼の要点:
   - 実装を読む前に、仕様と公開ヘッダだけから満たすべき性質を列挙する。
   - 実装と既存テストは変更しない。新しいテストファイルだけを足す。
   - 欠陥を見つけたら、失敗するテストを残して直さずに報告する。仕様が曖昧なものは「仕様の穴」として分ける。
   - ゴールデン音声に頼らず、解析的に期待値が分かる検査を重視する。並行部分はコードを読んで机上でも検証する。
3. 欠陥と仕様の穴を受け入れ側で読み、仕様の穴には決定を下して、実装担当に差し戻す（同じエージェントを再開する）。
4. 修正が戻ったら、独立テスト担当に「決定と食い違うテストの更新」と「修正が新しい欠陥を持ち込んでいないかの再確認」をさせる。新しい欠陥が出たら 3 に戻る。
5. 受け入れ側で、新しいビルドディレクトリから作り直して全構成を回し、要所のコードを読む。通ったら作業ブランチへ `--no-ff` でマージしてプッシュする。
6. 段階の終わりに `spec/interface/acceptance/stageN.md` に記録と持ち越し事項を書く。

ビルド構成（完了条件と受け入れチェックの両方で使う）:

```
cmake -S . -B <dir> -G Ninja && cmake --build <dir> && ctest --test-dir <dir> --output-on-failure
```

- gcc Debug、clang Debug（`-DCMAKE_CXX_COMPILER=clang++ -DCMAKE_C_COMPILER=clang`）
- gcc `-DSND_SANITIZE=address,undefined`、gcc `-DSND_SANITIZE=thread`
- gcc `-DCMAKE_BUILD_TYPE=Release`（テストあり）、`-DSND_BUILD_TESTS=OFF -DCMAKE_BUILD_TYPE=Release`
- dsp に触るときは `-DSND_SIMD_SCALAR=ON` と `-DCMAKE_CXX_FLAGS="-mavx2 -mfma"` も
- 並行性のテストは TSan と Release で 20 回繰り返す（`ctest --repeat until-fail:20 -R <名前>`）
- ビルドディレクトリはリポジトリの外（`/tmp/...`）に作る

決まりごと:

- 例外・RTTI なし、警告ゼロ（`-Werror`）、サードパーティ依存なし（テストフレームワークも自前）。
- `contract/`、`tests/framework/`、`tests/mocks/`、ルートの `CMakeLists.txt`、`cmake/` は凍結。変えるのは受け入れ側が決めたときだけで、版を上げて `CONTRACTS.md` §7 に書く。
- LUDIARS の運用ファイル（CLAUDE.md、`spec/domains`、Excubitor カタログ、CI）は作らない（後で別途作る）。
- 受け入れ前のものは作業ブランチに入れない。

環境についての注意:

- gcc 13、clang 18、CMake 3.28、Ninja、4 コア。clang のサニタイザ用ランタイムは無い（clang + サニタイザは未確認のまま）。
- Opus のエージェントを 4〜5 体並列で走らせると、5 時間枠の利用上限に当たって全員が止まる（今日 2 回起きた）。エージェントには区切りごとにローカルコミットを作らせる。止まったら、解除後に同じエージェントへメッセージを送って再開する。
- バックグラウンドのコマンドは既定の時間制限（10 分）で止められる。TSan の繰り返しなど長いものは時間制限を延ばして実行する。
- エージェントの worktree は `.claude/worktrees/`（git の管理外）。別のセッションには引き継がれないので、必要なものはコミットして作業ブランチに入れる。

2. その独立テスト（Opus 1 体）と受け入れチェック。重点: 契約 1.1 の各項目が決定どおりか、bank ⇄ io ⇄ jobs の並行動作（取り消し、Shutdown の順序）、buildtool の出力が codec と dsp の実装と一致しているか、端から端までの統合テストが解析的な検査を持っているか。
3. マージしたら `spec/handoff/` を削除する（このディレクトリは引き継ぎ用の一時置き場）。
4. **段階2**。設計書 15.1 の段階2 と 12.1 の依存表に沿って組を切る。目安:
   - core（テーブル、コマンド、システム群、ボイス管理、バスグラフ、Parameter、カテゴリ。3D は段階3 でもよい）
   - source のうち Sample と Stream（core の内部 IF 越し。codec と io を使う）
   - platform の実デバイス 1 種（下の未決事項）と、オーディオスレッドの駆動（設計書 2.2）
   - api（C API の本実装と構成ルート）
   - 最低限のツール（ミキサーとプロファイラ）とライブリンクは、core が形になってから並行で始める
   core は他の全部の土台なので、先に core の骨格（テーブルとコマンド適用、レンダーの直列版）を 1 体で作り、受け入れてから source / api / デバイスを並列にするのが安全。
5. 段階2の完了条件の例（設計書 14 章）: 実ボイス 128 本で 1 ブロックの処理時間が予算の 30% 未満、初期化後のメモリ確保ゼロ、RT 安全性の検出ゼロ。dsp 単体では 128 ボイスで 14〜25% と測れている。

## 5. 段階2の担当者に必ず伝えること（`stage1.md` の持ち越しから）

- 締切に遅れた描画チャンクの扱いは契約 1.1 の D-43（レンダーリストとアキュムレータの 2 組、保留ボイス、`StragglersInFlight()`）。`jobs/include/snd/jobs/rt_workers.hpp` の SAFE POINT を読むこと。
- ワーカーがチャンクの番号を取った直後に止められると、そのチャンクは締切まで誰にも処理されない。待っている呼び出し側が代わりに処理する改善を core と一緒に入れる（A1-14）。
- sinc リサンプラの状態は、最大ピッチ比の既定（32）のままだと 1 チャンネルあたり約 1.5 KiB。core は `Config.maxPitchRatio`（既定 4）を渡す。比率 4 超の経路はスタックに約 32 KiB を置く（D-47）。
- Stream ソースでは `DecoderPool::Release` の世代つきの形だけを使う（A1-15）。
- バンクをまたぐ行参照は無く、共有オブジェクト（バス、カテゴリ、Parameter など）は使う側のバンクに複製されている。core は ID で同一視する（A1-16）。
- io の呼び出し側の責務: 1 つのチャンネル内で、チャンクを持たない要求を、プールの最後のチャンクを持つ要求の前に並べない。デコード側の `Pop` は `rec.epoch` と `Epoch()` を見比べる。
