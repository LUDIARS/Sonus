# サウンドライブラリ 設計書

版: 0.2（Fableレビュー反映済み） / 2026-11-15 / 本文Markdownは同じアーティファクトの `design.md`

## 1. 概要

ゲーム向けのサウンドランタイムをC++で書き、データ指向設計（DoD）でオーディオ処理の時間とメモリを固定の上限内に収める。調整はスタンドアロンのオーサリングツールから、実行中のゲームにライブ接続して行う。実装は複数のエージェントが並列で行う前提とし、着手前に契約（インターフェース・スキーマ）を凍結する（12章）。

| 要件 | 設計上の対応 | 章 |
| --- | --- | --- |
| 波形を動的に生成して再生 | オシレータ・ノイズ・グラニュラ・パッチ・コールバック・ユーザーバッファを「ソース」として統一 | 5 |
| ストリーミング再生 | IOスレッド＋デコードジョブ＋固定チャンクのリング、同期グループ | 6, 8.4 |
| CRI ADX / Unity 相当のエフェクト・再生処理 | 機能対応表（同等/近似/対象外）で網羅を管理 | 7 |
| オーサリング/調整用の外部ツール | スタンドアロンアプリ＋TCPライブリンク＋上書き層 | 11 |
| クォンタイズとインタラクティブミュージックを簡単に設定 | 音楽時間での予約＋ステート×遷移ルール表 | 8 |
| 物理マテリアル別の再生 | 上位層モジュールで接触を間引き、材質の重ね合わせ＋組の上書き | 9 |
| スレッドプールでメモリ影響とスパイクに強くする | 固定ワーカー、初期化時の一括確保、先行レンダー、負荷LOD | 2, 3 |
| 複数エージェントでの並列実装 | モジュール分割、IF定義、列の所有者表、段階0「契約の凍結」 | 12, 15 |

### 1.1 前提

- 言語はC++20を想定。例外・RTTIなしでもビルドできるようにする。
- Unity等のエンジンには依存しない。組み込みはC++ APIと、PODとハンドルだけで構成するC APIで行う。
- 内部サンプル形式はfloat32、内部サンプルレートは固定（既定48kHz）。デバイスのレートが違う場合は最終段でリサンプルする。
- 対象プラットフォームと出力APIは未決（15章）。

### 1.2 設計原則

1. オーディオスレッドとリアルタイム（RT）ワーカーが使ってよいOS呼び出しは、アトミック操作、事前に作った同期プリミティブでの起床と待機、単調時計の読み出しだけ。メモリ確保・ロック・ファイルIO・書式付きログは禁止する。
2. メモリは初期化時に予算どおり一括確保する。予算を超える要求は確保失敗にせず、仮想化・間引き・再生拒否（理由付き）で吸収する。
3. データは種類ごとの連続配列（SoA）に置き、ハンドルと安定インデックスで参照する。処理はブロック単位でまとめて回す。
4. 重い処理はジョブで先回りし、オーディオスレッドは結果を消費するだけにする。
5. 決定論は範囲を決めて保証する（2.5）。

### 1.3 用語

| 用語 | 意味 | CRI ADXでの近い概念 | Unityでの近い概念 |
| --- | --- | --- | --- |
| Event | ゲームが鳴らす単位。トラックとロジックを持つ | キュー | AudioSource＋AudioClip / AudioRandomContainer |
| Track | Event内の並列レイヤー | トラック | — |
| Clip | トラック上に置く音素材またはソース | ウェーブフォーム | AudioClip |

| Playback | Eventの再生インスタンス | 再生ID | 再生中のAudioSource |
| Voice | 1本の波形を描く最小単位 | ボイス | （内部） |

## 2. 全体アーキテクチャ

スレッドは役割ごとに固定し、オーディオスレッドの仕事を「コマンド適用 → ロジック → レンダー」のブロック単位の一本道にする。1ブロックは既定256サンプル（48kHzで約5.3ms）。

[[ARCH_DIAGRAM]]

縦の一本道が音の流れ、左がその先回りをするジョブとIO、右がツールからの変更経路。

| スレッド | 役割 | しないこと | 優先度 |
| --- | --- | --- | --- |
| ゲーム側の登録スレッド | APIをコマンドとして記録し、`Update()`で公開。コールバックを受け取る | オーディオ側との待ち合わせ | ゲーム依存 |
| オーディオスレッド | デバイスに起こされ、ブロックごとにコマンド適用、ロジック、レンダー | 原則1の禁止事項 | 最高（RT） |
| RTワーカー × N | レンダーのチャンク処理だけ | 原則1の禁止事項 | オーディオスレッドと同じ |
| 通常ワーカー × M | デコード、バンク検証と登録準備、IR変換などの重い準備 | — | 通常 |
| IOスレッド | 非同期読み込みと帯域配分 | デコード | 通常 |
| ライブリンク | ツールとの送受信。変更はコマンドで投入 | ランタイムデータへの直接書き込み | 低 |
| デバイスコールバック | 出力リングからコピーし、オーディオスレッドを起こす | 計算全般 | OS依存 |

### 2.1 スレッド間通信

- **生産者ごとのSPSC**: コマンドを出すスレッド（ゲームの各登録スレッド、ライブリンク、ローダー経路）はそれぞれ専用のSPSCキューを持つ。オーディオスレッドはブロック先頭で、登録順の固定順序で全キューを取り込む。同じ生産者内の順序は保証し、生産者間の順序は保証しない。
- **コマンドバッファの循環**: ゲーム側はフレームごとの線形アリーナにコマンドを積み、`Update()`でアリーナごと公開する。取り込み済みのアリーナは返却用の逆向きSPSCで戻る。アリーナはスレッドごとに固定数（既定3）。
- **記録時の溢れ処理**: アリーナが満杯なら、その場で（ゲームスレッド上で）優先度の低い再生要求から記録を拒否する。停止・パラメータ・解放系は予約領域に記録し、必ず届ける。
- **ハンドルの払い出し**: Playback、Emitter、Transportのスロットはゲーム側が空きリストを持ち、記録時にインデックスと世代を決めて即座に返す。スロットは、オーディオスレッドが終了を報告した後の`Update()`で空きに戻る。空きが無ければ無効ハンドルを返す。
- **オーディオ → ゲームの通知**: 終了とエラーは、Playbackスロットごとの「終了フラグ＋理由」の固定配列で返すので、量に関係なく失われない。拍・マーカー・ログは固定容量のイベントリングで返し、溢れたら捨てて件数だけ数える。配送は`Update()`内、ゲームスレッド上で行う。
- **読み出し系API**: 再生状態、再生位置、メータ値は、オーディオスレッドが書くトリプルバッファから読む。返す値は「直近の`Update()`時点で一貫したもの」に限る。
- **`Update()`が途絶えたとき**: ロード中などで呼ばれなくても音は止めない。Emitterは速度で最大100ms（仮）外挿してから最終値で保持し、音楽は続ける。終了フラグは溜まり続け、次の`Update()`でまとめて届く。

### 2.2 駆動と遅延予算

- **駆動**: デバイスコールバックが出力リングからコピーした後、オーディオスレッドを起こす。オーディオスレッドは「リングの残量が目標を下回る限り」ブロックを描き続け、満たしたら眠る。コールバックの無い出力APIではタイマーで起こす。
- **先行量の定義**: 目標残量は「デバイス周期＋`renderAheadBlocks`ブロック」（既定2）。デバイス周期がブロックの倍数でなくても、残量で判断するので問題ない。
- **アンダーラン**: リングが空のとき、コールバックは最後のフレームを短くフェードアウトして無音を出し、回数を記録する。共通クロックは失った分も進め、音楽とゲームの時間を合わせたままにする。復帰時の追い付き描画は1回に最大2ブロック（仮）。
- **最終段リサンプル**: 内部レートとデバイスのレートが違う場合、出力リングの手前で変換する。

| 遅延の要素 | 既定 | リズムゲーム向けの例 |
| --- | --- | --- |
| API呼び出しから受理まで | 最大で`Update()`の間隔（60fpsで16.7ms） | 同左。音楽同期は予約（8章）で吸収する |
| ブロック | 256サンプル（5.3ms） | 128サンプル（2.7ms） |
| 先行レンダー | デバイス周期＋2ブロック | デバイス周期＋1ブロック |
| デバイスバッファ | 機種依存 | 機種の最小値 |

### 2.3 並列描画とワーカー

- **チャンクの状態**: レンダーリストはチャンクに分け、各チャンクを「未着手 → 着手 → 完了」の3状態でアトミックに管理する。オーディオスレッド自身も未着手のチャンクを取って処理する。
- **締切**: 未着手が無くなった時点で着手中のチャンクがあれば、有限時間（既定50µs、仮）だけスピンして待つ。それでも終わらないチャンクは、そのブロックでは出力に加えず（該当ボイスは前ブロック末尾から短くフェード）、遅れて届いた結果は世代番号で捨てる。回数は負荷LODの入力にする。
- **優先度**: RTワーカーはオーディオスレッドと同じ優先度・同じスケジューリンググループに置く（OSのオーディオ用ワークグループ機能などを使う。機種別の方法は要確認）。これで優先度逆転を避ける。
- **ワーカーの起床**: ブロックごとにセマフォで起こす。起床と待機は原則1で許可した呼び出しに含まれる。
- **通常ワーカー**: 先読み（デコード）と背景（バンク準備、IR変換）の2レーン。ワークスティーリングで分散する。
- **ホストのジョブシステム**: `IJobSystem`で相乗りできるのは通常ワーカーの仕事だけ。RTの仕事は常に自前のRTワーカーで動かす。

### 2.4 スパイクと過負荷

役割を分ける。単発のスパイクは先行レンダーで吸収し、持続する過負荷は負荷LODで下げ、入力のバーストは記録時と上位層で間引く。

- **予算の定義**: 1ブロックの実時間 × 目標使用率（既定60%、仮）。毎ブロック、ロジックとレンダーの処理時間を計測する。
- **負荷LOD**: 予算を連続8ブロック（仮）超えたら1段下げ、64ブロック（仮）余裕が続いたら1段戻す。段は順に、実ボイス上限を下げる、新規ボイスのリサンプラを軽量版にする、優先度の低いバスのエフェクトをバイパスする。
- **切り替えの作法**: リサンプラの切替は新規ボイスから適用する。エフェクトのバイパスは入力を止めてテールが鳴り終わってから行う（`IsTailDone`、12.3）。
- **重い準備の前倒し**: コンボリューションのIR変換、グラニュラの解析、ストリーム先頭のデコードは、バンク読み込み時か再生要求の受理時に通常ワーカーで行う。
- **デノーマル**: オーディオスレッドと全ワーカーでFTZ/DAZ相当を設定する。リバーブ等のテールで負荷が跳ねるのを防ぐ。

### 2.5 決定論の範囲

- **保証すること**: 「適用ブロック番号付きで記録したコマンド列」と同じバンクから、ロジックの決定（どのEventがいつ鳴り、どのClipが選ばれ、どの遷移が起きたか）は一致する。乱数はPlaybackごとのシードから作る。
- **条件付きで保証すること**: 波形のビット一致は、同一ビルド・同一SIMD経路・負荷LOD無効・ストール無しのときだけ。チャンクの加算はチャンク番号順に固定するので、並列化そのものは結果を変えない（3.4）。
- **保証しないこと**: Callback、Input、ストリームのストール、アンダーランが絡む出力。
- **リプレイ用の記録**: コマンド列と適用ブロック番号、負荷LODの段の変化、ストールの発生ブロックを記録する（11.3）。

### 2.6 プラットフォームのライフサイクル

- サスペンド時はデバイスを止め、共通クロックも止める。レジューム時は先行レンダーを満たしてから再開する。
- 出力デバイスの変更（ヘッドホン抜き差し等）は`IOutputDevice`の通知で受け、チャンネル構成を切り替えてバスの最終段で再ダウンミックスする。
- フォーカス喪失時の扱い（無音、継続、カテゴリ単位）は設定で選ぶ。

## 3. データ指向設計

すべての実行時データを「種類ごとのテーブル（SoA）」に置き、処理を「テーブルを順に舐めるシステム」として並べる。オブジェクト指向の仮想関数ツリーは使わない（プラグインIFだけは例外）。

### 3.1 テーブルと参照規則

- **格納**: 各テーブルは固定容量の密配列＋疎インデックス（sparse set）。削除は末尾と入れ替えて詰め、反復は密配列を先頭から回す。
- **外部参照**: 64bitハンドル（スロット番号32bit＋世代32bit）。解放済みハンドルへの操作は世代不一致で無視する。
- **テーブル間の参照**: 必ずスロット番号（安定インデックス）で持ち、密配列の位置は保存しない。密配列の位置はシステムの反復中だけ有効。
- **可変長の子**: Parameter値やセンドは、Playbackスロットに紐づく固定幅配列（例 8個）に置く。溢れた分は固定サイズブロック（16個単位）のプールから鎖でつなぐ。
- **ホット/コールド分離**: 毎ブロック触る列と、まれに触る列（Event ID、デバッグ名、統計）を別配列にする。

| テーブル | 主な列（ホット） | 件数の上限 |
| --- | --- | --- |
| Playback | eventId, state, schedule, seed, emitterSlot, transportSlot | 設定（例 1024） |
| Voice | sourceKind, sourceSlot, playhead, pitch, gain, busSlot, priority, audibility, realSlot | 仮想ボイス上限 |
| RealVoice | voiceSlot, resamplerState, filterState, panMatrix | 実ボイス上限＋フェード予備 |
| Emitter | position, velocity, forward, lastUpdateBlock, occlusion | 設定 |
| Listener | position, velocity, forward, up, weight | 最大4 |
| Spatial | emitterSlot×listenerSlotごとの距離、角度、減衰、ドップラー比 | Emitter上限 × リスナー数 |
| ParamValue | current, target, rampRate（スコープ別に3表: Global / Emitter / Playback） | 設定 |
| Bus | parentSlot, gain, sendRange, effectRange, peak | バンクの合計＋開発用予備 |
| Stream | fileId, readPos, ringRange, state, syncGroup | 同時ストリーム上限 |
| Transport | tempoMap, position, state, pitch | 設定（例 8） |
| Reservation | transportSlot, musicalTime, action, target | 設定（例 256） |

### 3.2 システムの並びと列の所有者

各列を書くのは1つのシステムだけにする。前のブロックの値を使う箇所は明示する。

| 順 | システム | 読む | 書く |
| --- | --- | --- | --- |
| 1 | ApplyCommands | コマンド | 各テーブルの生成・破棄、ParamValue.target、Emitter、Listener |
| 2 | UpdateTransport | 共通クロック、Transport、Reservation | Transport.position、発火リスト |
| 3 | EvaluateLogicParams | ParamValue | ParamValue.current（ランプ）、スイッチ値 |
| 4 | RunEventLogic | Playback、スイッチ値、発火リスト | Playback、Voiceの生成と終了 |
| 5 | Compute3D | Emitter（外挿・補間済み）、Listener | Spatial |
| 6 | EvaluateDspParams | ParamValue、Spatial、前ブロックのバスゲイン | Voice.gain / pitch、フィルタ目標値 |
| 7 | SelectVoices | Voice.priority、Voice.audibility（前ブロックのバスゲインとダッキングを使う） | RealVoiceの割り当て |
| 8 | BuildRenderList | RealVoice、Voice | レンダーリスト（バス → ソース種別の順にソート） |
| 9 | Render | レンダーリスト、ソース、DSP状態 | チャンク別アキュムレータ、Bus出力、DSP状態、playhead |
| 10 | Publish | 各テーブル | トリプルバッファ、終了フラグ、イベントリング |

### 3.3 メモリ

初期化時に`Config`の予算から全領域を確保し、以後オーディオスレッドでは確保しない。予算はすべてユーザーが渡す`IAllocator`から取る。

| 区分 | 確保の時点 | 上限の決め方 | 足りないときの挙動 |
| --- | --- | --- | --- |
| テーブル群 | 初期化時 | 各上限 × 列サイズ | 低優先度から仮想化、または再生拒否（理由付き） |
| フレームアリーナ | 初期化時 | 直列区間（ロジック）の作業領域 | 起きない設計。超過はアサート＋負荷LOD |
| スレッド別アリーナ | 初期化時 | （RTワーカー＋オーディオスレッド）× 固定サイズ | 並列区間の一時領域。チャンクを細かくし直す |
| ストリームプール | 初期化時 | 固定サイズのチャンク × 個数 | 優先度の低いストリームを止める、または仮想化 |
| デコーダプール | 初期化時 | コーデック別の状態サイズ × 同時数 | 再生拒否（理由付き） |
| DSPインスタンスプール | 初期化時 | バンクのビルド時に算出した必要量＋予備 | バンク読み込みを失敗させる |
| PCMキャッシュ | 初期化時 | 固定サイズページ × 個数、LRU | 6.2の規則 |
| バンク | 読み込み時（通常ワーカー） | ユーザー管理 | 読み込み失敗を通知 |

- 並列区間（レンダー）の一時領域はスレッド別アリーナだけを使い、フレームアリーナは直列区間専用にする。
- バンクのデータはリリースビルドでは読み取り専用。解放はエポック方式で、オーディオスレッド・全ワーカー・IO・未完了のデコードジョブがすべて参照を手放したことを確認してから戻す。
- メモリ使用量は区分ごとに集計し、ライブリンクとAPIで見られるようにする。

### 3.4 数値とSIMD

- 内部はfloat32、バッファは64バイト境界に揃える。チャンネルは非インターリーブ。
- SIMDは薄い抽象（SSE/AVX/NEON）を1つ用意し、DSPと3D計算はこれ越しに書く。
- 並列描画では、チャンクごとにバス別のアキュムレータへ加算し、最後にオーディオスレッドがチャンク番号順に足し合わせる。加算順が固定なので、ワーカー数や実行順で結果が変わらない。

## 4. 再生パイプライン

ゲームの`Play`はPlaybackを作るだけで、実際に何本のVoiceを鳴らすかはEventのロジックとボイス管理が決める。

1. ゲームが`Play(event, emitter, when)`を記録し、ハンドルを即座に受け取る。
2. オーディオスレッドが受理し、即時ならPlayingへ、予約付きならPendingへ、ストリームの準備が要るならPrimingへ進める。
3. Eventのシーケンス種別に従ってClipを選び、Voiceを生成する。
4. ボイス管理が実ボイス／仮想ボイスに振り分ける。
5. 実ボイスはリサンプル → ボイスエフェクト → パン → 出力先バスへ加算。
6. バスはエフェクトチェーン → センド → 親バスへ。最後にマスターバス → 出力リング。

### 4.1 Playbackの状態

| 状態 | 意味 | 次の状態 |
| --- | --- | --- |
| Pending | 予約時刻を待っている | Priming / Playing / Ended（取り消し） |
| Priming | ストリームの頭出しとデコード待ち | Playing / Ended（失敗） |
| Playing | 再生中（ボイスが仮想でも含む） | Paused / Stopping |
| Paused | 一時停止。再生位置は保持 | Playing / Stopping |
| Stopping | フェードアウトやテールの再生中 | Ended |
| Ended | 終了。理由（完了、停止、奪われた、拒否、破棄、エラー）を付けて通知 | — |

### 4.2 Eventのシーケンス種別

ポリフォニック、ランダム、ランダム（直前と重複なし）、シーケンシャル、シャッフル、スイッチ（パラメータ値で選択）、コンボシーケンシャル（一定時間内の連続呼び出しで順送り）、レイヤー＋パラメータでのクロスフェード。加えて次を持つ。

- **ランダム幅**: 音量、ピッチ、パン、開始位置、フィルタに、Clip単位で乱数の幅を付けられる。
- **アクショントラック**: トラック上の時刻に「他のEventを再生・停止」「Parameterを設定」「スナップショットを適用」を置ける。
- **入れ子**: ClipとしてほかのEventを置ける（循環はビルドで検出）。
- **ワンショット**: ハンドルを受け取らない再生（`PlayOneShot`）。Unityの`PlayOneShot`相当。

### 4.3 Parameterのスコープと合成

- **スコープ**: Global（全体で1つ）、Emitter（そのEmitterで鳴る全Playbackが参照）、Playback（その再生だけ）。同じParameterが複数スコープで設定された場合は、Playback → Emitter → Global の順に優先する。
- **ランプ**: Parameterごとに追従速度（単位/秒）を持ち、`EvaluateLogicParams`がブロック単位で目標値へ近づける。
- **カーブの合成**: 1つの対象に複数のカーブが掛かるとき、音量はdBで加算、ピッチはセントで加算、ローパスのカットオフは最小値、ハイパスは最大値、その他は乗算。

### 4.4 ボイス管理

- **並べ方**: 優先度を主キー、可聴度（3D減衰・音量・前ブロックのバスゲインとダッキングから推定した音量）を副キーにする。毎ブロックの全件ソートはせず、上位N件の部分選択を行う。
- **ヒステリシス**: 実ボイスの入れ替えは、新しい候補の可聴度が現職を一定値（既定3dB、仮）上回ったときだけ行う。
- **上限の階層**: 全体の実ボイス上限、ボイスリミットグループ（例: 足音最大8）、Event単位の上限、同一Eventの再トリガー間隔。
- **奪い方**: 最も古い / 最も小さい / 最も優先度が低い / 奪わない（新規を拒否）をグループごとに選ぶ。奪われたボイスは短いフェードを掛け、その間はフェード用の予備実ボイス枠（既定8、仮）を使う。
- **仮想ボイス**: 描画しないが再生位置は進める。可聴度が戻れば実ボイスに戻る。戻り方は「続きから」「先頭から」「戻らない」を選べる。ストリームの戻りは6.3に従う。
- **サンプル精度の開始**: 開始時刻はブロック内オフセットまで持ち、ブロックの途中から鳴らせる。

### 4.5 3Dと空間

- **位置の補間**: Emitterの位置はゲームフレーム単位で届くので、速度で外挿したうえでブロック間を線形補間し、パンとドップラーの階段状の変化を防ぐ。
- **計算の単位**: 3D計算はEmitter × Listenerの組ごとに1回行い、結果を`Spatial`表に置く。ボイスは参照するだけ。
- **複数リスナー**: 合成方式を「最も近いリスナー」（既定）、「重み付き合成」、「リスナー別の出力（画面分割）」から選ぶ。
- **距離カーブ**: 音量、ローパス、スプレッド、リバーブセンド量、3Dブレンド（2Dと3Dの混合率）を距離のカーブで指定できる。
- **形状**: 点、コーン（指向性）、範囲音源（線・面・箱）。遮蔽・閉塞はゲームから渡すParameterで扱う（レイキャストはゲーム側）。
- **空間化プラグイン**: HRTF等はバス単位またはボイス単位の`IDspEffect`として差し込める。

### 4.6 バスグラフとミックス

- バスは木構造（親子）＋センド（プリ/ポストフェーダー）。グラフはビルド時に依存順へ並べた配列にしておき、実行時は配列を順に処理する。独立した枝はRTワーカーで並列化する。
- **スナップショット**: バス音量・エフェクト値の組を名前で保存し、時間付きで遷移する。複数を重みで重ねがけできる。
- **ダッキング**: サイドチェーン（入力バスのレベルで対象を下げる）と、ルール型（指定カテゴリのEventが鳴っている間だけ下げる。CRIのREACT相当）の両方。
- **カテゴリ**: バスとは別に、Eventにタグとして付ける。カテゴリ単位で音量・ミュート・ポーズ・ソロができる。「ポーズを無視する」カテゴリ（UI音など。Unityの`ignoreListenerPause`相当）を指定できる。
- **出力**: スピーカー構成（ステレオ、5.1、7.1等）ごとのダウンミックスを最終段で行う。コントローラーのスピーカーや振動など別出力への送り先も、出力バスとして表現する。
- **ラウドネス計測**: マスターと任意のバスで計測値（短期・統合）をメータとして読めるようにする（測定方式は実装時に決める）。

## 5. 波形の動的生成

動的生成はサンプル再生と同じ「Source」の一種として扱い、Event・バス・3D・ボイス管理はすべて共通で使える。

| Source種別 | 内容 | 主なパラメータ |
| --- | --- | --- |
| Sample | メモリ上の波形。読み込み形式は6.2の4種 | ループ点、開始オフセット |
| Stream | ストリーミング（6章） | ループ点、プリロード量 |
| Oscillator | サイン・ノコギリ・矩形・三角・パルス（PolyBLEPで折り返し抑制）、ウェーブテーブル | 周波数、デューティ、テーブル位置 |
| Noise | ホワイト・ピンク・ブラウン | 色、シード |
| Granular | サンプルからグレインを生成 | 密度、長さ、位置、ピッチ揺らぎ |
| Patch | ツールで組む小さな合成グラフ（Osc → Filter → Env 等） | ノード上限あり |
| Callback | ユーザー関数が波形を書き込む | ユーザーデータ |
| UserBuffer | 実行時にゲームが登録したPCMバッファを鳴らす（Unityの`AudioClip.Create`/`SetData`相当） | ループ、書き込み位置 |
| Input | マイク等の外部入力、別システムの出力 | — |

### 5.1 実行方式

- `BuildRenderList`がソース種別ごとにボイスをまとめ、種別ごとのループで描く。ボイスごとの仮想関数呼び出しはしない。
- Patchはビルド時にノードを依存順に並べた配列へ変換し、実行時は配列を順に処理する小さなインタープリタで動かす。中間バッファはスレッド別アリーナから取る。
- モジュレータ（ADSR、LFO、ランダム、パラメータカーブ、エンベロープフォロワー）はブロック単位で評価し、サンプル単位の線形補間でジッパーノイズを防ぐ。
- UserBufferは、ゲームが`IAllocator`由来ではない自前のメモリを渡す。書き込みと読み出しの境界はアトミックな書き込み位置で管理し、ゲームは読み出し位置より先の領域だけを書き換える。

### 5.2 Callbackの約束

```cpp
using SynthCallback = void (*)(void* user, float* const* out, uint32_t channels,
                               uint32_t frames, const snd::RenderContext& ctx);
```

- **既定は先行描画**: Callbackは通常ワーカー上で、専用リングへ数ブロック先（既定4ブロック、仮）まで描く。レンダーはリングから読むだけなので、ユーザー関数の遅れが他のボイスを巻き込まない。代わりにその分の遅延が付く。
- **締切の判定は事後**: リングが空になったら、そのボイスは無音で埋めて警告を出し、以後はリングに十分たまるまで鳴らさない。実行中の関数を中断しようとはしない。
- **低遅延モード（オプトイン）**: RTワーカー上で同期的に呼ぶモード。ロック・確保・IOは禁止（テストビルドで検出、14章）。締切を超えたボイスは次のブロックからミュートし、そのCallbackを先行描画モードに降格する。
- ゲームから値を渡すときは`SetParam`を使う。Callbackは`ctx`から補間済みの値を読む。

## 6. ストリーミングとコーデック

ストリームは「IOで圧縮データを先読み → デコードジョブでPCM化 → レンダーが消費」の3段のリングで流し、各段は固定サイズのチャンクだけを扱う。

### 6.1 流れ

1. **プリロード**: ストリームの先頭チャンク（既定は約100ms分、仮）をバンクに同梱し、`Play`の瞬間に鳴らし始められるようにする。音楽の入口マーカー（8.3）にも同様のプリロードを付けられる。
2. **IO**: IOスレッドがチャンク単位で非同期に読む。読み出し順は優先度（音楽 > ボイス > 環境音、設定で変更可）と、100msあたりのバイト数で決めた帯域予算で決める。
3. **デコード**: 読めたチャンクを先読みレーンのジョブでPCMリングに展開する。先読み目標は「再生速度 × 目標時間（例 200ms、仮）」で、ピッチが高いほど多く読む。目標を下回ったストリームから順にデコードする。
4. **消費**: レンダーはPCMリングから読むだけ。

### 6.2 Sampleの読み込み形式

| 形式 | 中身 | 向いている用途 | Unityでの近い設定 |
| --- | --- | --- | --- |
| PCM常駐 | 展開済みPCMをバンクに持つ | 短く頻繁に鳴る音 | Decompress On Load |
| 圧縮常駐 | 圧縮データを持ち、再生時にボイス別の小リングへ先読みレーンでデコード | 中程度の長さ | Compressed In Memory |
| 展開キャッシュ | 初回再生時にPCMキャッシュへ展開して使い回す | 繰り返し鳴る中くらいの音 | — |
| ストリーム | 6.1 | 長い音、音楽、ボイス | Streaming |

PCMキャッシュは固定サイズページ（例 64KB、仮）で管理し、再生中のデータは参照カウントで固定する。全ページが固定済みのときは、圧縮常駐と同じ経路で逐次デコードして鳴らし、それも不可なら理由付きで再生を拒否する。

### 6.3 状態と例外

- **ストール**: データが間に合わなければ短いフェードで無音にして回数を記録する。再開位置はストリームの属性で選ぶ。「時間優先」は経過分を飛ばして現在位置から再開（音楽の既定）、「音優先」は止まった位置から再開（ボイスの既定）。
- **仮想化からの復帰**: ストリームのボイスが仮想化された間は位置だけ進め、IOは止める。復帰時はシークしてPrimingを経るので遅延が出る。復帰方針（続きから・先頭から・戻らない）はストリーム属性で決める。
- **ループとつなぎ**: ループ点はサンプル精度。ループ終端に近づいたらIOが先頭側を先読みする。音楽のセグメント連結も同じ仕組みで切れ目なくつなぐ。
- **シーク**: シーク表（コーデックのフレーム境界とファイル位置の対応）をビルド時に作る。
- **上限**: 同時ストリーム数とストリームプールの総量は固定。超えた要求は優先度の低いものから止めるか、仮想化する。

### 6.4 コーデック

- PCM、ADPCM（CPUが軽い、ブロック単位でシーク可能）、Opus（圧縮率が高い）を標準にする。CRIのHCAは独自形式なので対象外。
- コーデックは`ICodec`（12.3）で差し替え可能にする。機種固有のハードウェアデコーダもこれで扱う。
- デコーダの状態はデコーダプールから取る。サイズは`ICodec::StateBytes`で問い合わせる。
- Opusはフレーム長がブロックと合わないため、デコード結果はボイス別リングで吸収する。エンコーダ遅延（プリスキップ）とシーク時のプリロールはビルド時にメタデータとして持たせ、ループ点がサンプル精度で合うよう補正する（Opus固有の推奨値は要確認）。

### 6.5 ファイルアクセス

`IFileSystem`（12.3）をユーザーが実装できる（パック、暗号化、機種固有IO）。既定実装も用意する。呼ばれるのはIOスレッドからだけ。

## 8. クォンタイズとインタラクティブミュージック

すべての再生要求に「いつ鳴らすか」を拍・小節単位で指定でき、予約は音楽時間のまま保持して毎ブロック判定する。音楽の切替は「ステート × 遷移ルール表」を埋めるだけで設定できる。

### 8.1 時間軸とトランスポート

- **共通クロック**: オーディオスレッドが進める64bitのサンプルカウンタ。サスペンド以外では止まらない（2.2のアンダーラン時も進む）。
- **トランスポート**: テンポマップ（BPMの変化点）、拍子、再生位置（小節・拍・tick、1拍960tick）を持つ時間軸。音楽Eventを再生すると1つ作られ、そのPlaybackが所有する。リズムゲーム等のために`CreateTransport`で単独でも作れる。
- **状態**: Stopped、Playing、Paused。シークとループ区間を持てる。
- **実行時の変更**: `SetTempo(transport, bpm, when)`でテンポを変えられる（テンポマップへの上書き）。トランスポートのピッチ（再生速度）を変えると、テンポとピッチが連動して変わる。
- **ゲームへの通知**: 拍・小節・マーカーの通知に「その瞬間がスピーカーから出る推定時刻」を付ける。出力遅延は`IOutputDevice::OutputLatencySeconds`（12.3）から得る（機種ごとの精度は要確認）。

### 8.2 予約（クォンタイズ）

`When`で次のどれかを指定する。どの`Play`・`Stop`・`SetMusicState`・`SetTempo`にも付けられる。

- すぐ（`Immediate`）
- 次の拍 / 次の小節 / Nの小節後 / 指定グリッド（1/8、1/16など）
- 次のマーカー / セグメント終端
- オフセット付き（アウフタクト: 頭拍より前から鳴る素材は、頭拍の位置を素材内のマーカーで持ち、逆算して早めに鳴らす）

予約の扱い:

- **音楽時間で保持**: 受理時に「どのトランスポートの何小節何拍何tick」に変換して`Reservation`表に入れる。サンプル時刻にはまだしない。
- **毎ブロック判定**: `UpdateTransport`が、現在ブロック＋先読み時間の範囲に入った予約を発火させ、その時点でサンプル位置へ変換する。テンポ変更やシークが途中で起きても、予約は新しい時間軸に従う。
- **最小先読み時間**: 受理から発火までに「1ブロック＋対象のプライム時間（ストリームの頭出しとデコード、メモリ上の素材なら0）」が必要。足りないときの動作は遷移ルールの「間に合わない時」列（8.5）で決め、指定が無ければ次のグリッドへ送る。
- **ゲームから見た遅延**: API呼び出しから受理までの`Update()`間隔ぶんは別に掛かる。「呼んだ瞬間の次の拍」を厳密に狙う用途では、ゲーム側が拍通知を見て1拍前に予約する。ツールは各予約先の最小先読み時間を表示する。

### 8.3 音楽の構造

| 要素 | 役割 | CRI ADXでの近い概念 |
| --- | --- | --- |
| Segment | 小節単位の音楽素材。入口・出口マーカーと、入口前の助走（ピックアップ）・出口後の余韻を持つ | ブロック |
| Playlist | Segmentの並び、ループ回数、ランダム選択 | ブロックシーケンス |
| Stem | 縦方向のレイヤー。パラメータ（例: 緊張度）で音量を変える | トラック＋AISAC |
| State | 横方向の状態（探索、戦闘、ボス等）。各StateはPlaylistを持つ | — |
| Transition | State間の移り方のルール（8.5） | ブロック遷移 |
| Stinger | グリッドに合わせて重ねる短いフレーズ | — |

- 遷移では、出ていくSegmentの余韻と、入ってくるSegmentの助走が重なる。重なっている間のボイス数もボイス管理の対象にする。
- **入口の頭出し**: 「同じ小節位置から」入る遷移のために、Segmentの入口マーカーごとにプリロードチャンクをビルドで同梱できる（チェックボックスで指定）。
- **事前プライム**: 現在のStateから遷移ルールで行けるStateのうち「事前準備」を付けた遷移先は、ストリームプールの予算内で先にプライムしておく。`PrepareMusicState`で明示的にも指示できる。

### 8.4 同期グループとストール

- 1つの音楽Playbackに属するストリーム（Stem、遷移先、つなぎ素材）は同期グループになり、開始・シーク・ストールをグループ単位で扱う。
- Stemは多チャンネル1ファイル（インターリーブ）を推奨形にし、ストリーム1本で同期を保証する。別ファイルのStemも同期グループで扱えるが、ストール時のずれは「時間優先」で吸収する。
- ストール方針はグループ単位で選ぶ。「時間優先」（既定）はトランスポートを進め続け、間に合わなかった部分は無音にして現在位置から再開する。拍通知はゲームとずれない。「音優先」はデータが来るまでトランスポートごと止める。

### 8.5 遷移ルール表（設定の中心）

上から順に照合し、最初に一致した行を使う。具体的な行を上に、ワイルドカードの既定ルールを最下行に置く。ツールは特定度の高い順に自動で並べ替え、到達できない行を警告する。

| From | To | タイミング | フェード（出 / 入） | つなぎ素材 | 開始位置 | 割り込み | 間に合わない時 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Explore | Battle | 次の拍 | 0.5拍 / なし | Battle_Intro | 先頭 | 可 | 次の拍へ送る |
| Battle | Explore | 次の小節 | 2拍 / 2拍 | なし | 前回位置 | 可 | 次の小節へ送る |
| * | Boss | セグメント終端 | なし / なし | Boss_Transition | 先頭 | つなぎ完走後 | 遅れて開始 |
| * | * | 次の小節 | 1拍 / 1拍 | なし | 先頭 | 可 | 次の小節へ送る |

- フェードの拍数は、出側は遷移元のテンポ、入側は遷移先のテンポで数える。
- 開始位置は「先頭」「同じ小節位置」「指定マーカー」「前回位置（そのStateを最後に離れた位置）」から選ぶ。拍子が違うState間の「同じ小節位置」は、小節番号を遷移先Segmentの長さで割った余りの小節の頭拍にする。

### 8.6 遷移の状態機械

| 状態 | 新しい`SetMusicState`が来たとき |
| --- | --- |
| Idle（Stateを再生中） | 一致するルールを探し、Pendingへ。同じStateの要求は無視 |
| Pending（タイミング待ち） | 目標Stateを上書き（最後の要求が勝つ）。ルールは新しい目標で引き直す |
| Transitioning（フェード・つなぎ素材の再生中） | ルールの「割り込み」が「可」なら、いま聞こえている位置から新しい遷移を始める。「つなぎ完走後」なら1件だけ保留し（最後の要求が勝つ）、完了後に処理する |

- Stingerは予約付きの`Play`として扱う。同じStingerの予約が重なったら、後の要求で置き換えるか積むかをStingerごとに選ぶ。

### 8.7 「簡単に設定できる」ための仕掛け

- ツールが素材のメタデータ（BPM、拍子、マーカー）を読み込み、無ければタップテンポと波形上のグリッド合わせで決められる。
- 既定ルール1行だけで動き始め、気になる遷移だけ行を足せばよい。
- ゲーム側のAPIは`SetMusicState`と`SetParam`の2つで足りる。
- ツール上でStateボタンを押すと、実際のルールで遷移を試聴できる（ライブ接続中ならゲーム内でも）。
- タイムライン表示で、遷移がどの拍で起きたか、どの予約が「間に合わない時」の規則で送られたかを後から確認できる。

## 9. 物理マテリアル別再生

物理マテリアルは、公開APIだけを使う上位層モジュール（ゲームスレッドで動く）として作る。物理エンジンからの大量の接触をここで間引き、材質の単体音の重ね合わせを基本に、組ごとの専用音で上書きする。

### 9.1 マテリアルの対応付け

- ゲームの物理マテリアル（多数）を、サウンドマテリアル（少数、例: 金属、木、石、土、草、水、布、ガラス）に対応表で写す。
- 「濡れ」「砂利混じり」などは別マテリアルにせず、表面パラメータとしてEventに渡す（レイヤーの音量で混ぜる）。

### 9.2 入力

```cpp
struct Contact {
  uint64_t     objectA, objectB;      // ゲーム側の物体ID（クールダウンと追跡に使う）
  uint16_t     materialA, materialB;  // サウンドマテリアルID
  ContactKind  kind;                  // Impact / Slide / Roll / Break
  float        position[3];
  float        normal[3];
  float        impulse;               // 衝撃量 [N·s]
  float        relativeSpeed;         // 相対速度 [m/s]
  float        massA, massB;          // [kg]
};

void SubmitContacts(PhysicsAudio*, const Contact* contacts, uint32_t count, float dtSeconds);
void PlayFootstep(PhysicsAudio*, EmitterHandle foot, uint16_t footMaterial,
                  const SurfaceWeight* surfaces, uint32_t surfaceCount, Motion motion);
```

足音はアニメーションイベントから呼ぶのが一般的なので、接触とは別のAPIにする。地形の材質ブレンドは重み付きの複数材質で受け、重みの大きい2つまでを鳴らして重みを音量に写す。

### 9.3 鳴らす音の決め方

- **既定は重ね合わせ**: 材質Aの単体音と材質Bの単体音を両方鳴らす。N種類の材質に対してN個の設定で済む。
- **組の上書き**: 特別な組（例: 金属×ガラス）だけ専用Eventを設定する。対称なN×N表を平坦な配列にし、`table[min(a,b) * N + max(a,b)]`の1回の参照で上書きの有無を調べる。
- **代替順**: 組の上書き → 各材質の既定を重ねる → 全体の既定。代替が起きたことはツールで一覧できる。
- **強さの写し方**: ツールのカーブで決める。衝撃量 → ベロシティレイヤー（弱・中・強）と音量、質量 → ピッチ、相対速度 → 擦れ音の音量とピッチ。

### 9.4 間引き（スパイク対策）

`SubmitContacts`は配列を受け取り、1回のSoAパスで次を行う。

1. 衝撃量が閾値未満の接触を捨てる。
2. 位置を格子に丸め、同じ格子・同じマテリアル組の接触を1つにまとめる（衝撃量は最大値、個数はParameterとして渡す）。
3. 物体ごと・組ごとのクールダウン中のものを捨てる。
4. 残りを衝撃量で並べ、時間あたりの予算（例 毎秒300件、仮。`dtSeconds`でフレームあたりに換算）までを再生要求にする。

### 9.5 継続する接触

擦れ・転がりは物体ペアのキーで追跡し、最初の報告で開始、以後は速度Parameterを更新、一定時間報告が無ければフェードアウトして止める。追跡表とクールダウン表は固定容量で、溢れたら最も古いものから追い出す。

位置だけ指定するワンショット（`PlayAt(event, position)`）も用意し、破片などEmitterを作るほどでない音に使う。

## 10. データ形式とビルド

ツール側は差分を取りやすいテキストのプロジェクト、ランタイム側はそのままメモリに載せられるバイナリのバンクに分け、CLIのビルドツールで変換する。

### 10.1 プロジェクトとID

- Event・Bus・Parameter・音楽・マテリアル表などを1オブジェクト1ファイルのJSONで保存する。IDはGUID。
- ランタイムIDは名前からの32bitハッシュ。衝突検出はバンク単位ではなくプロジェクト全体（DLCを含む）で行い、衝突はビルドエラーにする。
- ビルドはID表（名前・ハッシュ・GUID）を成果物として出し、ゲームコード用のヘッダも生成する。ゲームコードは`"SE/Explosion"_id`のようにコンパイル時ハッシュでも参照できる。
- リネームしたときは旧名を別名として残し、旧名の参照も解決できるようにする。

### 10.2 バンクのバイナリ

- ヘッダ: マジック、形式の版、機種、エンディアン、アライメント（64バイト）、チェックサム、依存するバンクの一覧、チャンク目次。
- チャンク: SoA配置のテーブル群、常駐の波形データ、プリロードチャンク、シーク表、DSPプールの必要量、文字列表（リリースでは外せる）、GUID対応表（開発ビルドのみ）。
- ポインタは使わずオフセットで持ち、読み込んだら補正なしで使える。
- ストリーム用の波形はバンクとは別ファイルにし、IOのセクタ境界に揃えて置く。
- バイト単位の仕様は段階0で凍結する（12.4）。

### 10.3 読み込みと解放

- **経路**: IOスレッドが読む → 通常ワーカーが検証（チェックサム、版、依存）してDSPインスタンスを準備 → 登録コマンドを投入 → オーディオスレッドがブロック境界で参照表を差し替える。専用のローダースレッドは置かない。
- **依存**: 依存先のバンクが未ロードなら登録しない。依存元がロードされている間は、依存先を解放できない。
- **解放**: `UnloadBank(bank, mode)`。`StopAndUnload`は参照中のPlaybackを短いフェードで止めてから登録を外し、`IfUnused`は参照中なら失敗を返す。登録を外した後、エポック（3.3）で全員の参照が切れてからメモリを戻す。
- **機種別変換**: コーデック、サンプルレート、チャンネル数を機種ごとに設定し、変換結果は内容ハッシュでキャッシュする（差分ビルド）。

### 10.4 多言語ボイス

言語別のボイスバンクを、同じイベントIDの集合として作る。`SetLanguage`で読み込むバンクを切り替える。再生中のボイスは切り替え前の言語のまま最後まで鳴らす。

## 11. オーサリングツールとライブ接続

ツールはランタイムと同じC++のDSPコードを使うスタンドアロンアプリにし、ツールで聞いた音とゲームで鳴る音を一致させる。UIはDear ImGuiを第一候補とする（Qtとの比較は15章）。

### 11.1 主な画面

- Eventエディタ（トラックとクリップのタイムライン、シーケンス種別、ランダム幅、アクション）
- ミキサー（バスの卓表示、センド、エフェクト、スナップショット、ダッキング、カテゴリ）
- パラメータとカーブのエディタ（スコープ、追従速度、合成規則の確認）
- 3D減衰プレビュー（上から見た図でリスナーとエミッタを動かして試聴）
- 音楽エディタ（テンポ・拍子・マーカー、Playlist、Stem、State、遷移ルール表、遷移試聴、最小先読み時間の表示）
- マテリアル表エディタ（単体音、組の上書き、代替の一覧、強さカーブ）
- 波形生成パッチエディタ
- プロファイラ（ボイス、CPU、メモリ区分、ストリーム、負荷LODの段、イベントログ）

### 11.2 ライブ接続

- ゲームに組み込んだランタイムが待ち受け、ツールがTCPで接続する（コンソールは開発機ネットワーク経由）。リリースビルドではマクロで丸ごと外す。
- メッセージはバージョン付きのバイナリ形式。スキーマは段階0で凍結する。
- **接続時の照合**: プロトコルの版とプロジェクトのビルドハッシュを照合する。不一致なら、ツールが差分のオブジェクトをすべて送るか、接続を拒否するかを選ぶ。

| 方向 | 内容 |
| --- | --- |
| ツール → ゲーム | 値の変更（GUID → ランタイムID＋項目＋値）、オブジェクトの差し替え（再ビルドしたチャンク）、試聴再生、Parameter・Stateの上書き |
| ゲーム → ツール | 再生中のボイスとEvent、ブロック処理時間、メモリ使用量、ストリームのストール、負荷LODの段、イベントログ、バスのメータ（約30Hz） |

- **上書き層**: 開発ビルドではバンクのテーブルを書き込み可能なメモリに読み、値の変更はコマンドとしてブロック境界でその場に書き込む。バスやエフェクトの追加など構造の変更は、開発用の予備容量（`Config.devReserve`）の範囲で受け付け、超えたらバンクの再ビルドとホットリロードに回す。
- **大きな差し替え**: 波形の差し替え等は通常の読み込み経路で新しい領域に読み、参照を差し替えたあと古い領域をエポックで解放する。
- **切断時**: ツールが切断しても、上書きした値はそのまま残る（ゲームを再起動すればバンクの値に戻る）。
- ライブ中の変更はツール側のプロジェクトに保存する。正しいデータは常にツール側にある。

### 11.3 記録と再生

開発ビルドで、コマンド列（適用ブロック番号付き）、負荷LODの段の変化、ストールの発生を記録できる。ツールで再生すると、2.5の範囲で同じ結果が得られる。不具合報告とテストの両方に使う。

### 12.3 内部インターフェース（骨子）

```cpp
namespace snd {

struct IAllocator {   // 初期化時と通常ワーカー（バンク読み込み）からだけ呼ぶ
  virtual void* Allocate(size_t bytes, size_t align, MemTag tag) = 0;
  virtual void  Free(void* p, MemTag tag) = 0;
};

struct IJobSystem {   // 通常ワーカーの仕事専用。RTの仕事は渡さない
  virtual void Submit(const JobDesc* jobs, uint32_t count, JobLane lane) = 0;
  // 契約: Submitはどのスレッドから呼ばれてもよい。キャンセルはJobDesc::cancelFlagで協調的に行う。
  //       完了はJobDesc::doneCounterのアトミック減算で通知する。
};

struct IFileSystem {  // IOスレッドからだけ呼ぶ
  virtual FileId   Open(const char* path) = 0;
  virtual bool     ReadAsync(FileId, uint64_t offset, void* dst, uint32_t bytes, IoToken) = 0;
  virtual IoStatus Poll(IoToken) = 0;
  virtual void     Close(FileId) = 0;
};

struct ICodec {       // 通常ワーカー（先読みレーン）から呼ぶ。状態はデコーダプールから
  virtual uint32_t StateBytes(const CodecHeader&) const = 0;
  virtual void     Init(void* state, const CodecHeader&) = 0;
  virtual uint32_t Decode(void* state, const uint8_t* src, uint32_t srcBytes,
                          float* const* dst, uint32_t maxFrames) = 0;
  virtual void     Seek(void* state, uint64_t frame) = 0;  // プリロールはヘッダのメタデータに従う
};

struct IDspEffect {   // RTワーカーとオーディオスレッドから呼ぶ。状態はDSPインスタンスプールから
  virtual uint32_t StateBytes(const EffectDesc&) const = 0;
  virtual void     Init(void* state, const EffectDesc&, uint32_t sampleRate) = 0;
  virtual void     Process(void* state, const float* const* in, float* const* out,
                           uint32_t channels, uint32_t frames, const ParamBlock&) = 0;
  virtual bool     IsTailDone(const void* state) const = 0;
};

struct IOutputDevice {
  virtual bool     Open(const DeviceDesc&, DeviceCallback cb, void* user) = 0;
  virtual uint32_t PeriodFrames() const = 0;
  virtual uint32_t SampleRate() const = 0;
  virtual double   OutputLatencySeconds() const = 0;            // 拍通知の補正に使う
  virtual void     SetEventListener(DeviceEventFn fn, void* user) = 0;  // 変更、サスペンド
};

}  // namespace snd
```

標準エフェクトは仮想関数を通さず、種別ごとのループでまとめて処理する。`IDspEffect`はプラグイン用。

### 12.4 並列実装の進め方

- 段階0は1人（1エージェント）で行い、凍結したヘッダとスキーマを全員の入力にする。
- 以後は依存の浅いモジュールから並列に着手する。各モジュールはモックに対して単体で完結させ、完了条件（14章のテスト）を満たしてから統合する。
- 契約の変更は、変更提案 → 影響モジュールの合意 → 版を上げて反映、の手順に限る。

## 13. 公開API

記録系の関数はコマンドを積んで即座に戻り、ハンドルや即時のエラーコードを返す。非同期の結果（終了、読み込み完了、エラー）は`Update()`内のコールバックで届く。無効なハンドルへの操作は何もしない。

### 13.1 一覧

| 分類 | 関数 | 呼べるスレッド |
| --- | --- | --- |
| システム | `Create`, `Destroy`, `Update`, `RegisterThread`, `Suspend`, `Resume` | `Create`/`Destroy`/`Update`は所有スレッド、他は登録スレッド |
| バンク | `LoadBankAsync`, `UnloadBank`, `GetBankState`, `SetLanguage` | 登録スレッド |
| 再生 | `Play`, `PlayOneShot`, `PlayAt`, `Stop(fade, when)`, `Pause`, `Resume`, `SetScheduledStop` | 登録スレッド |
| 3D | `CreateEmitter`, `DestroyEmitter`, `SetTransform`, `SetListener` | 登録スレッド |
| Parameter | `SetParam`（Global / Emitter / Playback）, `SetSwitch` | 登録スレッド |
| ミックス | `SetBusVolume`, `ApplySnapshot(weight, time)`, `SetCategoryVolume`, `PauseCategory`, `MuteCategory` | 登録スレッド |
| 音楽 | `SetMusicState`, `PrepareMusicState`, `CreateTransport`, `SetTempo`, `SeekTransport` | 登録スレッド |
| 物理 | `SubmitContacts`, `PlayFootstep`（physicsモジュール） | ゲームスレッド |
| 動的生成 | `PlaySynth`, `CreateUserBuffer`, `WriteUserBuffer`, `PlayInput` | 登録スレッド（`WriteUserBuffer`は任意のスレッド） |
| 問い合わせ | `GetPlaybackState`, `GetPosition`, `GetMeter`, `GetStats` | 任意のスレッド（直近の`Update()`時点の値） |
| 通知 | `SetCallbacks`（終了、マーカー、拍、エラー、読み込み完了） | 所有スレッド |

- 未ロードのEventを`Play`すると、無効ではないハンドルを返し、次の`Update()`で理由「未ロード」の終了通知を出す。ハンドルの扱いを呼び出し側で分岐させないため。
- `Create`の失敗（予算不足、デバイス無し）はエラーコードで返す。
- C APIは同じ関数をPODとハンドルだけで提供する。C++ APIはその薄いラッパーにする。

### 13.2 使用例

```cpp
snd::Config cfg;
cfg.sampleRate        = 48000;
cfg.blockSize         = 256;
cfg.renderAheadBlocks = 2;
cfg.maxRealVoices     = 128;
cfg.maxVirtualVoices  = 1024;
cfg.memory.streamPoolBytes = 8u << 20;
cfg.memory.pcmCacheBytes   = 16u << 20;
cfg.jobs.realtimeWorkers   = 2;
cfg.jobs.external          = &myEngineJobs;  // 任意: 通常ワーカーの仕事だけを委ねる

snd::System* sys = nullptr;
if (snd::Create(cfg, &myAllocator, &myFileSystem, &sys) != snd::Result::Ok) { /* ... */ }
snd::LoadBankAsync(sys, "Common.bank");

// 通常の再生
snd::EmitterHandle e = snd::CreateEmitter(sys);
snd::SetTransform(sys, e, pos, forward, velocity);
snd::PlaybackHandle p = snd::Play(sys, "SE/Explosion"_id, e);
snd::SetParam(sys, p, "Size"_id, 0.8f);

// クォンタイズ（音楽の次の小節頭で鳴らす）
snd::Play(sys, "Music/Stinger"_id, snd::kNoEmitter,
          snd::When::NextBar(musicTransport));

// インタラクティブミュージック
snd::SetMusicState(sys, music, "Battle"_id);
snd::SetParam(sys, music, "Intensity"_id, 0.7f);

// 物理接触を一括で渡す（physicsモジュール）
snd::phys::SubmitContacts(physicsAudio, contacts.data(), contacts.size(), dt);

// 動的生成
snd::SynthDesc sd{};
sd.callback = &MyEngineSound;
sd.user     = &engineState;
sd.channels = 1;
sd.mode     = snd::SynthMode::Buffered;  // 既定。LowLatencyはオプトイン
snd::PlaySynth(sys, sd, e);

// 毎ゲームフレーム: コマンド公開とコールバック配送
snd::Update(sys);
```

## 14. テスト戦略

| 種類 | 内容 | 主な対象 |
| --- | --- | --- |
| 単体 | モジュールごとに、モック相手で完結するテスト | 全モジュール |
| ゴールデン音声 | 固定のコマンド列を描画し、保存済みの出力と比較する（許容差を設定） | dsp, core, source, music |
| 決定論 | 同じコマンド記録を2回再生し、ロジックの決定とビット一致（2.5の条件下）を確認 | core, music |
| RT安全性 | テストビルドで、オーディオスレッドとRTワーカー上の確保・ロック・IOをフックして検出する | 全RT経路、低遅延Callback |
| 負荷・バースト | 実ボイス上限の4倍の要求、1フレーム1000件の接触、ストリーム上限超え、IOの遅延注入 | core, physics, io |
| 機能カバレッジ | 7章の表の行ごとに、設定意図どおりに振る舞うことを確認 | 全体 |
| ファズ | 壊れたバンクとライブリンクのメッセージを入力しても落ちないこと | bank, livelink |

段階1の完了条件の例: 実ボイス128本で1ブロックの処理時間が予算の30%未満、初期化後のメモリ確保ゼロ、RT安全性の検出ゼロ。

## 15. 開発ロードマップと未決事項

### 15.1 段階

0. **契約の凍結**: 12.2の7項目。以後の全段階の前提。
1. **基盤（並列）**: base / platform / jobs、dsp、codec / io、bank / buildtool を並列に作る。
2. **コア**: core と Sample・Stream ソース、出力バックエンド1種。最低限のツール（ミキサーとプロファイラ）とライブリンクもここから並行して始める。
3. **カバレッジ**: 3D、標準DSP一式、Parameter（3スコープ）、スナップショット、ダッキング、カテゴリ、ボイス管理の全機能。完了条件: 7章の全行にテストがある。
4. **音楽と物理（並列）**: music と physics。
5. **ツールの完成**: 全画面、記録と再生。
6. **拡張**: Granular、Patch、コンボリューション、ルーム／ポータル、タイムストレッチ、対象機種の追加。

### 15.2 未決事項

- 対象プラットフォームと出力API（PC、コンソール、モバイルのどれか）。
- ツールのUI技術（Dear ImGui か Qt か）。
- 標準コーデックの最終選定と、機種固有ハードウェアデコーダへの対応範囲。
- 空間オーディオ（HRTF、アンビソニックス、オブジェクトベース出力）の要否。
- ボイス数、メモリ予算、CPU予算、遅延の目標値（機種ごと）。
- 本文中の「仮」の数値（先行ブロック数、スピン時間、LODの閾値、ページサイズ等）の確定。
- 既存のCRI / Unityプロジェクトからの移行ツールは要るか。
- 将来Unityから使う予定があるか（あるならC APIの形を段階0で確定する）。
